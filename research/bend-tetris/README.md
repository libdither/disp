# Bend Tetris

Tetris written in [Bend](https://crates.io/crates/bend-lang) 0.2.38 (Bend 1, which runs on the HVM2 runtime), playable in a terminal or in a browser as WebAssembly.

- `hello.bend`: hello world. `bend run-c hello.bend` prints it.
- `tetris.bend`: the game. It's two pure functions, `step(game, key)` and `draw(game)`, plus a loop in `main` that reads one byte from stdin, steps, and prints the frame as ANSI text. A 0 byte is a gravity tick, which the host sends every 50 ms.
- `tetris.html`: the game as one self-contained page (runtime and WebAssembly inline). Open it from disk. It's generated by `build.sh`.
- `build.sh`: builds `build/tetris` for the terminal, and `tetris.html`.
- `host/`: what runs the compiled game. `patch.py` adapts the C that `bend gen-c` emits, `host.c` is the IO loop, `hvm.js` and `page.html` are the browser side.

## Play

In a browser, open `tetris.html`. In a terminal:

```sh
cargo install hvm bend-lang          # bend 0.2.38, hvm 2.0.22
pip install ziglang                  # or any zig on PATH; only needed for the web page
ZIG="python -m ziglang" ./build.sh
./build/tetris
```

Arrows (or wasd / hjkl) move, rotate and soft-drop. Space hard-drops, p pauses, r restarts, q quits.

## Why not just `bend run-c tetris.bend`

It works, but each frame takes about 2.5 s. HVM2's IO loop reads the output string back one byte at a time and re-normalizes the net after each byte. Each normalize spawns the worker threads, and each thread spins up to 256 times before noticing there is no work. The host here avoids that, and fixes what a long-running game needs:

- **One thread, no spin.** The evaluator runs inline and stops as soon as it is out of work. This takes a frame from ~2.5 s to ~11 ms natively, and ~6 ms as WebAssembly in V8.
- **No leaks.** HVM2's readback never frees what it reads, which costs about 4 nodes and 3 wire variables per byte printed. That's harmless on its 4 GB heap, but a browser-sized heap (4M nodes) runs out within a few hundred frames. `host.c` reads each constructor, detaches its arguments, and links the leftover shell to an eraser so HVM's own interaction rules free it. A 20,000-event soak test (5,476 frames) ends with zero live nodes.
- **A loop that can wait.** HVM2's IO loop blocks on stdin. `host.c`'s `resume()` returns when the game asks for a byte that hasn't arrived, so a browser can feed it keys and ticks between animation frames. The same loop drives the terminal build, where `main` polls stdin with a 50 ms timeout to make ticks.
- **Interpreted, not compiled.** `bend gen-c` also compiles every definition to C. For this program that's no faster (IO dominates), and the WebAssembly is 2.3 MB instead of 200 KB.

`patch.py` checks every patch applies exactly, so a different Bend or HVM version fails at build time rather than at runtime.

Bend 2 ([`research/awesome-langs/bend2.md`](../awesome-langs/bend2.md)) drops HVM for compiled C and is a different language; none of this carries over to it.
