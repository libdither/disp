## KQ1. Gradual typing: what the unknown type `?` buys and what it costs

### Takeaway
`?` (Siek & Taha 2006) buys a static checker that only rejects *inconsistencies among the known parts* of types and defers the rest to run-time casts; the price is (a) replacing type equality by a non-transitive "consistency" relation, (b) run-time casts with blame, (c) a monotonicity law (the gradual guarantee, 2015) that the design must satisfy, (d) a soundness *spectrum* (three incompatible enforcement semantics, 2018), and (e) large measured slowdowns in sound implementations (2016).

### Cited Findings
- (2006) The unknown type is a hole *inside a type*, and the static job is reduced to consistency of known parts: "The unknown portions of a type are indicated by ?" and "The job of the static type system is to reject programs that have inconsistencies in the known parts of types" — [Siek & Taha 2006, Scheme Workshop, p.2](http://scheme2006.cs.uchicago.edu/13-siek.pdf#page=2). Status OK. Relevance: the first formal "don't know" at the type level; a run-time cast is the deferred obligation. For disp, `?` is the analogue of "not yet checked".
- (2015) The gradual guarantee is the monotonicity law relating precision to behaviour: "a new formal property, named the gradual guarantee, that relates the behavior of programs that differ only with respect to their type annotations" — [Siek, Vitousek, Cimini, Boyland 2015, SNAPL, p.1](https://drops.dagstuhl.de/storage/00lipics/lipics-vol032-snapl2015/LIPIcs.SNAPL.2015.274/LIPIcs.SNAPL.2015.274.pdf#page=1); and informally "The gradual guarantee says that if a gradually typed program is well typed, then removing type annotations always produces a program that is still well typed" — [same, p.6](https://drops.dagstuhl.de/storage/00lipics/lipics-vol032-snapl2015/LIPIcs.SNAPL.2015.274/LIPIcs.SNAPL.2015.274.pdf#page=6). Status OK (Dagstuhl open access; the DOI resolver 404s, the storage URL works). Relevance: for a budgeted checker the same law reads "less budget / less precision can only move a verdict toward 'unknown', never flip proven to refuted".
- (2009) Blame assigns a failed deferred check to a side: the blame calculus works "by decomposing the usual notion of subtype into positive and negative subtyping" so that "well-typed programs can't be blamed" — [Wadler & Findler 2009, ESOP, p.1](https://homepages.inf.ed.ac.uk/wadler/papers/blame/blame.pdf#page=1). Status OK. Relevance: an evidence-carrying failure verdict; the more precisely typed side is provably never at fault.
- (2016) Abstracting Gradual Typing (AGT) gives `?` an abstract-interpretation semantics: "Gradual typing integrates an unknown type ? and a notion of type consistency into a pre-existing static type system"; `?` is the abstraction α of a set of static types with "Proposition 3 (α is Sound). If T̂ is not empty, then T̂ ⊆ γ(α(T̂))", and "run-time checks naturally arise by deducing evidence for consistent judgments during proof reduction" — [Garcia, Clark, Tanter 2016, POPL, p.1](https://www.cs.ubc.ca/~rxg/agt.pdf#page=1). Status OK. Relevance: the unknown type *is* an abstract value; "evidence" attached to consistent judgments is a formal partial-verdict object. This is the cleanest bridge from gradual typing to the Kleene/abstract-interpretation view in KQ6.
- (2016) Measured cost of sound gradual typing: "the few emerging implementations suffer from performance overheads due to these checks", and the paper's method evaluates every typed/untyped module configuration — [Takikawa, Feltey, Greenman, New, Vitek, Felleisen 2016, POPL, p.1](https://www2.ccs.neu.edu/racket/pubs/popl16-tfgnvf.pdf#page=1). Status OK. Relevance: deferring a check to run time is not free; the cost scales with the number of typed/untyped boundaries crossed.
- (2018) Soundness is a spectrum, not a bit: "The literature on gradual typing presents three fundamentally different ways of thinking about the integrity of programs that combine statically typed and dynamically typed code" — the higher-order ("natural"), erasure, and first-order ("transient") embeddings, each with its own soundness theorem and performance profile — [Greenman & Felleisen 2018, ICFP, p.1](https://www2.ccs.neu.edu/racket/pubs/icfp18-gf.pdf#page=1). Status OK. Relevance: shows that "what a passed check means" is a design knob; a cheaper run-time check (transient) buys speed by weakening what the static type guarantees.
- (2018) Graduality as a semantic ordering: "embedding-projection pairs (ep pairs) are to graduality what relations are to parametricity", refining Siek et al.'s dynamic gradual guarantee into an error-approximation order — [New & Ahmed 2018, ICFP, p.1](https://arxiv.org/pdf/1807.02786#page=1). Status OK. Relevance: this is the "G" of the fire triangle in KQ2; casts between a type and a less precise type must form an ep pair (upcast then downcast is a no-op; downcast then upcast may only error more).
- (2019) Gradual Type Theory (GTT) prices the unknown type against the equational theory: "uniqueness principles for gradual type connectives show that if the βη laws hold for a connective, then casts between that connective must be equivalent to the so-called 'lazy' cast semantics" — [New, Licata, Ahmed 2019, POPL, p.1](https://arxiv.org/pdf/1811.02440#page=1). Status OK. Relevance: if you want casts to respect βη reasoning, the cast semantics is forced; this is the metatheoretic price of `?` stated as a theorem rather than a benchmark.

### Inferences
- `?` is a "don't know" that is *resolved by evidence at run time*; disp's "no counterexample within budget" is a "don't know" that is *resolved by more budget*. The gradual guarantee is the right template for the law a budgeted checker must satisfy: monotone in precision/budget.
- AGT's α/γ reading suggests a direct formalization for disp: a type that is "unknown within budget k" denotes the set of all types consistent with the facts established in k steps.
- The Greenman–Felleisen spectrum warns that a cheaper checker that only verifies constructors ("first-order") gives a strictly weaker meaning to "accepted"; any claim that disp's cheap checker agrees with the canonical one must say *which* soundness it preserves.

- No 2025–2026 primary source on new gradual-typing metatheory surfaced in this pass (searches returned 2006–2024 items); "state as of Oct 2026" here rests on absence of findings, not on a confirmed survey.
- Unverified (do not link): none in this KQ; all eight sources verified.

## KQ2. Gradual dependent types: approximate normalization, the fire triangle, GRIP, GTT

### Takeaway
The fire triangle (Lennon-Bertrand, Maillard, Tabareau, Tanter 2022) says a gradual dependent type theory cannot have all of **N** (normalization), **G** (graduality, in the New–Ahmed ep-pair sense) and **C** (conservativity over CIC, which includes closure of universes under Π). Each system drops a corner: GCIC^G drops N; GCIC^N keeps N and C but "does not fully validate G"; GCIC↑ keeps N and G but is conservative only over CIC↑ (Π types bumped one universe up); GRIP (2022) keeps N and C and restricts G to "self-precise" terms; GDTL (Eremondi, Tanter, Garcia 2019) sidesteps the triangle by making *compile-time* normalization approximate-but-total and *run-time* execution exact-but-possibly-divergent, with a "normalization gradual guarantee" (monotonicity of approximate results in precision).

### Cited Findings
- (2019) Approximate normalization splits the phases: "compile-time normalization is approximate but total, while runtime execution is exact, but may fail or diverge. We prove that GDTL has decidable typechecking and satisfies all the expected properties of gradual languages. In particular, GDTL satisfies the static and dynamic gradual guarantees"; and "we were led to establish a novel normalization gradual guarantee that captures the monotonicity of approximate normalization with respect to imprecision" — [Eremondi, Tanter, Garcia 2019, ICFP, p.1](https://arxiv.org/pdf/1906.06469#page=1). Status OK. Relevance: the closest existing formal object to disp's budgeted check. Approximate normalization returns `?` where exact normalization might loop; the normalization gradual guarantee is exactly the theorem a budgeted checker needs ("more precision/budget gives a more precise, never contradicting, normal form").
- (2022) The GCIC paper's own characterization of GDTL: "A key idea of GDTL is to adopt an approximate form of computation at compile-time, called approximate normalization, which ensures termination and totality of typing, while adopting a standard gradual reduction semantics with errors and non-termination at runtime" and "for typing, it uses Approximate Normalization (AN), which always produces ?_A as a result of going through imprecision and back" — [Lennon-Bertrand, Maillard, Tabareau, Tanter 2022, TOPLAS, pp.2 and ~15](https://arxiv.org/pdf/2011.10618#page=15). Status OK. Relevance: fixes the corner GDTL gives up: type-level computation through `?` collapses to `?` (losing information rather than normalization), so G in the ep-pair sense is not what GDTL claims; it claims the (weaker) gradual guarantees plus decidability.
- (2022) The fire triangle, stated: "a gradual type theory cannot satisfy at the same time normalization, graduality, and conservativity with respect to CIC" — [GCIC, p.5](https://arxiv.org/pdf/2011.10618#page=5). The abstract phrases C's load-bearing part as "closure of universes under dependent product". Proof idea (same paper, §2): "The quintessential example of non-termination in the untyped lambda calculus is the term Ω := δ δ where δ := (λx. x x) … when introducing gradual types, one usually expects to accommodate such idioms"; with `? → ?` consistent with `?` plus G, Ω is well typed and diverges. Status OK.
- (2022) The three corners, each dropped once (verbatim from §3): "(1) GCIC^G … This results in a theory that is not normalizing." — [GCIC, p.15](https://arxiv.org/pdf/2011.10618#page=15); "(2) GCIC↑: a theory that satisfies both N and G, and supports C with respect to CIC↑", where "CIC↑ is a subset of CIC, with a stricter constraint on universe levels. In particular CIC↑ loses the closure of universes under dependent product that CIC enjoys" (the universe of Π A B is the *successor* of the max of the levels, not the max) — [GCIC, p.15](https://arxiv.org/pdf/2011.10618#page=15); "(3) GCIC^N: a theory that satisfies both C/CIC and N, but does not fully validate G. This theory uses the universe hierarchy at the computational level to detect potential divergence. Such runtime check failures invalidate the DGG for some terms, and hence G, as well as the SGG." — [GCIC, p.16](https://arxiv.org/pdf/2011.10618#page=16). Status OK. Relevance: an exact map of what a "type = program" language with an unknown can keep. Note GCIC^N loses even the *static* gradual guarantee (SGG) for some terms, not only the dynamic one.
- (2022) GRIP, "A Reasonably Gradual Type Theory": restates the triangle — "three fundamentally desirable properties cannot be fully satisfied simultaneously: (1) strong normalization …" — [Maillard, Lennon-Bertrand, Tabareau, Tanter 2022, ICFP, p.2](https://arxiv.org/pdf/2209.00975#page=2) — and takes a fourth path: "By adopting a novel interpretation of the unknown term that carefully accounts for universe levels, GRIP satisfies graduality for a large and well-defined class of terms, in addition to being normalizing and a conservative extension of CIC" — [same, p.1](https://arxiv.org/pdf/2209.00975#page=1); the problematic terms are those that are not "self-precise" (more precise than themselves), and precision is *internalized* so GRIP can reason about its own graduality. Status OK. Relevance: shows the don't-know region can be *characterized inside the theory* (self-precision is a predicate the theory can state), which is attractive for disp where types are programs anyway.
- (2022) Gradual propositional equality carries evidence: "each equality proof is accompanied by a term that is at least as precise as the equated terms, acting as a witness of their plausible equality. These witnesses track partial type information as a program runs, raising errors when that information shows that two equated terms are undeniably inconsistent" — [Eremondi, Garcia, Tanter 2022, ICFP, p.1](https://arxiv.org/pdf/2205.01241#page=1). Status OK. Relevance: an evidence-carrying "plausibly equal" verdict; a refutation is produced only when evidence becomes "undeniably inconsistent", i.e. the three-valued pattern at the level of equality proofs.
- (2022) A fourth corner choice (student poster, abstract only): GrInd "has decidable type checking, the gradual guarantees, and conservative extension of CIC. It sacrifices strong normalization and graduality" — [Eremondi 2022, ICFP SRC page](https://icfp22.sigplan.org/details/icfp-2022-student-research-competition/9/Extinguishing-the-Fire-Triangle-of-Gradual-Dependent-Types#content). Status OK (conference HTML; no paper PDF). Relevance: separates the weaker *gradual guarantees* (kept) from *graduality* (dropped), and separates *decidable type checking* (kept) from *normalization* (dropped) — the same two separations disp's budget makes.
- (2024) Indexed inductive types are where gradual dependent types get hard: "the standard encodings of indexed inductive types in intensional type theory, e.g., using type-level fixpoints or subset types, break in the presence of gradual features"; the paper proposes PUNK, "a general framework to explore the design space" spanning eager and lazy cast reduction — [Malewski, Maillard, Tabareau, Tanter 2024, ICFP page](https://icfp24.sigplan.org/details/icfp-2024-papers/21/Gradual-Indexed-Inductive-Types#c2371058bcb9b31dd10e115e7f712708). Status OK for the conference page (abstract); the PDF itself could not be fetched (see Gaps). Relevance: disp types that are predicates over trees are closest to indexed families; this is the frontier as of 2024.
- (2018–2025) Gradual *verification* moves `?` into specification formulas: "the gradual guarantee, stating that the verifier will not flag static or dynamic errors for specifications that are correct but imprecise" and "an imprecise specification can be optimistically strengthened (in non-contradictory ways) by the verifier to support proof goals. Wherever such strengthenings occur, dynamic checks are inserted to preserve soundness" — [DiVincenzo et al., Gradual C0 (arXiv v3 2024; TOPLAS 2025), p.2](https://arxiv.org/pdf/2210.02428#page=2). Status OK. Relevance: "optimistically assume what you could not refute, then guard it dynamically" is the exact operational shape of accepting a "no counterexample within budget" verdict.
- (2019) GTT (the "Gradual Type Theory" named in the question) is the axiomatic, call-by-push-value account of graduality for *simple* gradual types (quote and link in KQ1); it is not dependently typed, but it is the source of the ep-pair notion of G that the fire triangle uses. Status OK.

### Inferences
- Disp's budgeted check is a fourth compromise the triangle already anticipates: the type language need not normalize (types are arbitrary programs), but the *checker* is total because of fuel; the "don't know" outcome is GDTL's `?_A` result. The triangle says this don't-know cannot be eliminated without paying in C or G.
- The property to prove for disp's checker is Eremondi et al.'s "normalization gradual guarantee" with budget playing the role of precision: budget k' ≥ k yields a verdict at least as definite and never contradictory.
- GRIP's "self-precise" class is a useful target: identify the sub-language of disp types for which the checker's verdicts are exact in bounded budget, and state graduality only there.

- Could not fetch the full text of "Gradual Indexed Inductive Types" (UChile repository returned a PHP error; no arXiv/HAL copy found); only the ICFP 2024 page abstract is verified.
- No 2025–2026 gradual dependent type paper surfaced in two searches; the GRAPA project page lists planned work (extending GRIP to a GCIC-like source language, indexed inductives), undated. As of 2026-10-09 the latest verified items are GRIP (ICFP 2022) and Gradual Indexed Inductive Types (ICFP 2024).

## KQ3. Soft and probabilistic typing: confidence, distributions, checker-as-likelihood

### Takeaway
Soft typing (Cartwright & Fagan 1991) never rejects a program; it inserts run-time checks where the inferred type cannot be proved. The ML-based line (JSNice 2015 → LambdaNet 2020 → TypeWriter 2020 → Typilus 2020 → Type4Py 2022 → TypeT5 2023) quantifies confidence as a CRF/softmax distribution or a similarity-space neighbourhood, reports top-k accuracy or MRR, and uses a *real type checker as a hard filter* (TypeWriter's feedback-directed search; Typilus's "optionally type checks 95%"; TypeT5's type-error count as "coherence"). OptTyper (2020) relaxes logical type constraints into a continuous optimisation producing per-identifier distributions. The only place a checker enters *as a likelihood inside inference* is the sequential-Monte-Carlo steering line (Lew et al. 2023; Loula et al. ICLR 2025), which explicitly sorts signals into cheap/incremental vs expensive and hard vs soft.

### Cited Findings
- (1991) Cartwright & Fagan, "Soft typing", PLDI '91 — bibliographic record verified via Crossref through `verify-source.sh` ("Soft typing | Robert Cartwright, Mike Fagan | 1991 | PLDI '91"); the ACM page is BLOCKED and no open-access PDF exists (Rice FTP hosts only a `.ps.Z`). Treat as unverified for quoting. Secondary explainer (verified): a soft type system must "accept all syntactically correct programs as input; produce equivalent, memory-safe programs as output; and be unobtrusive", with Fagan's "minimal text principle" (no annotations required) and "minimal failure principle" — [Greenman, PRL blog "What is Soft Typing?" 2017](https://prl.khoury.northeastern.edu/blog/2017/04/28/what-is-soft-typing/#what-are-the-design-criteria). Status OK (HTML). Relevance: the original "never say no" checker — statically unresolvable obligations become inserted run-time checks; the verdict is never "refuted", only "proved" or "guarded".
- (2015) JSNice: types as a MAP assignment of a CRF: "phrase the problem of inferring program properties as structured prediction … conditional random fields (CRFs) … joint prediction"; measured "its type annotation predictions are correct in 81% of the cases" — [Raychev, Vechev, Krause 2015, POPL, p.1](https://files.sri.inf.ethz.ch/website/papers/jsnice15.pdf#page=1). Status OK. Relevance: confidence is a graphical-model score; no checker in the loop.
- (2020) LambdaNet: the goal is to "output a probability distribution of types for each missing annotation" over a space of library types plus user-defined types — [Wei, Goyal, Durrett, Dillig 2020, ICLR, p.3](https://arxiv.org/pdf/2005.02161#page=3). Status OK. Relevance: types-as-distributions, explicitly.
- (2020) TypeWriter: neural proposals validated by a checker-driven search: "TypeWriter invokes a gradual type checker with different combinations of the predicted types, while navigating the space of possible type combinations in a feedback-directed manner"; result: "TypeWriter can fully annotate between 14% to 44% of the files in a randomly selected corpus, while ensuring type correctness" — [Pradel, Gousios, Liu, Chandra 2020, FSE, p.1](https://arxiv.org/pdf/1912.03768#page=1). Status OK. Relevance: the clearest precedent for "generator proposes, checker decides" with the checker as a hard oracle inside a search over a combinatorial space; the probabilistic model only orders the search.
- (2020) Typilus: open-vocabulary types via metric learning plus "an optional type checker"; "Typilus confidently predicts types for 70% of all annotatable symbols; when it predicts a type, that type optionally type checks 95% of the time"; "a type checker checks all predictions and filters incorrect ones" — [Allamanis, Barr, Ducousso, Gao 2020, PLDI, p.1](https://arxiv.org/pdf/2004.10657#page=1). Status OK. Relevance: confidence threshold ("confidently predicts") plus checker filter — a two-stage soft-then-hard verdict.
- (2022) Type4Py: similarity-space nearest-neighbour inference evaluated with MRR; the authors note "the neural models are not 100% confident in their first suggestion for all test samples" — [Mir, Latoškinas, Proksch, Gousios 2022, ICSE, p.7](https://arxiv.org/pdf/2101.04470#page=7). Status OK. Relevance: confidence reported as rank quality, trained on a type-checked dataset.
- (2023) TypeT5: seq2seq infilling with static-analysis-built contexts and iterative decoding; "produces more coherent results with fewer type errors", coherence being measured by the number of type errors a checker reports — [Wei, Durrett, Dillig 2023, ICLR, p.1](https://arxiv.org/pdf/2303.09564#page=1). Status OK. Relevance: the checker as a *metric* on the joint prediction, not as a filter.
- (2020/2021) OptTyper: "relaxing the logical inference problem of type prediction into a continuous optimisation problem"; the solution is a matrix where "each row is a probability vector (a discrete distribution over the T literal types)" — [Pandi, Barr, Gordon, Sutton, arXiv 2004.00348, p.1](https://arxiv.org/pdf/2004.00348#page=1). Status OK. Relevance: logical constraints relaxed to a differentiable likelihood over typings — the closest thing found to "type checking as a likelihood", but for *annotation* inference, not for program generation.
- (2023) SMC steering: "specify language generation tasks as posterior inference problems in a class of discrete probabilistic sequence models, and replace standard decoding with sequential Monte Carlo inference. For a computational cost similar to that of beam search, SMC can steer LLMs to solve diverse tasks, including infilling, generation under syntactic constraints" — [Lew, Zhi-Xuan, Grand, Mansinghka 2023, p.1](https://arxiv.org/pdf/2306.03081#page=1). Status OK. Relevance: constraints become potentials (likelihood factors) in a probabilistic program; particles that violate a hard constraint get weight 0.
- (2025) Explicit taxonomy of checker signals as potentials: "Checking (partial) code statically (type-checking, linting, partial evaluation)" is listed as a signal, and "Such signals vary along several important dimensions: some are cheap to compute (linting), others are more costly (simulations); some can be evaluated incrementally with each sampled token (language model critique), others provide sparser guidance (running code); some enforce binary hard constraints (type-checking), others yield soft continuous scores (scoring)" — [Loula et al. 2025, ICLR, p.1](https://arxiv.org/pdf/2504.13139#page=1). Status OK. Relevance: this is the closest published framing of disp's problem: a type checker used as a potential inside posterior inference, with an explicit cheap-incremental vs expensive distinction and a "weight correction" step for expensive potentials applied only at resampling points.

### Inferences
- In all the ML type-inference systems the *checker's* verdict is treated as certain; uncertainty lives entirely in the proposal distribution. None of them model P(well-typed | partial program) as a quantity.
- The SMC line is the right home for a budgeted checker: a cheap per-token potential (syntactic / prefix type check) plus an expensive, sparsely applied potential (the budgeted semantic check), with "unknown" naturally mapping to "do not zero the weight; do not fully trust either".
- Soft typing is the limiting case where the checker never refutes; gradual typing is soft typing with programmer-controlled precision; disp's budgeted check is soft typing where the inserted guard can be *paid for later with more budget* instead of at run time.

### Gaps
- No 2024–2026 primary source found that calibrates type-prediction confidence; the search returned general LLM-calibration surveys only.
- No source found that treats the *type-checking verdict itself* as a probability or likelihood other than via SMC potentials; this appears to be an open seam as of 2026-10-09.
- Unverified (do not link): Cartwright & Fagan 1991 PDF (ACM blocked; Crossref metadata only); Wright & Cartwright 1997 TOPLAS "A practical soft type system for Scheme" (ACM blocked; Crossref metadata only).

## KQ4. Typed holes and partial programs: Hazel, Hazelnut, Blinn et al. 2024, sketching

### Takeaway
Hazelnut (2017) proves every edit state is well typed after cursor erasure by inserting empty/non-empty holes; Hazel (2019) evaluates *around* holes ("indeterminate" results) and resumes evaluation when a hole is filled; the marked lambda calculus (POPL 2024) makes type-error localization *total*, so a meaningful partial program exists at every moment; Blinn et al. (OOPSLA 2024) feed the hole's expected type, the typing context, and type-relevant headers from the language server into the LLM prompt, with type information raising StarCoder2's correct-solution rate "by an order of magnitude" on a small from-scratch benchmark (MVUBench), plus a static error-correction round-trip. Program sketching (Solar-Lezama 2008) is the SAT/CEGIS ancestor; Smyth (2020) propagates examples backward through partially evaluated sketches.

### Cited Findings
- (2017) Hazelnut: "the sensibility theorem establishes that every edit state is well-typed after cursor erasure"; the calculus is bidirectionally typed and inserts holes automatically — [Omar, Voysey, Hilton, Aldrich, Hammer 2017, POPL, p.3](https://arxiv.org/pdf/1607.04180#page=3). Status OK. Relevance: totality of typing over partial programs is a theorem, obtained by making the type assigned to a hole (and to an ill-typed subterm wrapped in a non-empty hole) the gradual `?`.
- (2019) Hazel's edit actions "automatically insert empty and non-empty holes as necessary to guarantee that every edit state has some (possibly incomplete) type" — [Omar, Voysey, Chugh, Hammer 2019, POPL, p.21](https://arxiv.org/pdf/1805.00155#page=21); evaluation proceeds around holes, yielding "indeterminate" sub-expressions, and "when the programmer performs an edit that fills an empty expression hole or that replaces a non-empty hole with a type-correct expression, evaluation can resume from the previous evaluation state. We call this operation fill-and-resume" — [same, p.3](https://arxiv.org/pdf/1805.00155#page=3). Status OK. Relevance: "indeterminate" is a don't-know *value*; fill-and-resume is the incremental re-check after a hole is filled, which is exactly what a hole-by-hole generator needs.
- (2024) Marked lambda calculus: "we define a gradual type system for expressions with marked errors, which operate as non-empty holes, together with a total procedure for marking arbitrary unmarked expressions. We mechanize the metatheory … in Agda and implement it, scaled up, as the new basis for Hazel"; "The marked lambda calculus is bidirectionally typed, so localization decisions are systematically predictable based on a local flow of typing information" — [Zhao, Maroof, Dukkipati, Blinn, Pan, Omar 2024, POPL, p.1](https://hazel.org/papers/marking-popl24.pdf#page=1). Status OK. Relevance: the checker never gets stuck on an ill-typed partial program; it marks and continues, so a generator always has a typed sketch to work from.
- (2024) How hole context reaches the model: "The Hazel Language Server provides codebase-wide (B) semantic information relevant to the hole, collecting types based on the expected type (C) and selecting type-relevant headers from the context (D). These are combined into a contextualized text prompt (E) which is sent (F) to the LLM"; retrieval follows the expected type through type aliases and selects in-scope headers by type-directed similarity; a "Static Error Correction" pass asks the language server to localize errors in the completion and feeds them back — [Blinn, Li, Kim, Omar 2024, OOPSLA, pp.3–4](https://arxiv.org/pdf/2409.00921#page=1). Status OK.
- (2024) What was measured: models GPT-4-0613 and StarCoder2-15B on MVUBench (five model-view-update programs written from scratch; the sketch given is the type-annotated `update` header); "In the absence of any type or header information, StarCoder2 performed poorly. The addition of type information drastically improves performance, increasing the percentage of correct solutions by an order of magnitude. Furthermore, incorporating headers leads to an additional 50% increase in relative performance. However, two examples, BO and TO, experienced degraded performance after the inclusion of headers" — [same, p.19](https://arxiv.org/pdf/2409.00921#page=19); overall "We find that contextualization with type definitions is particularly impactful" and the techniques were ported to TypeScript; ChatLSP is proposed as a conservative LSP extension — [same, p.1](https://arxiv.org/pdf/2409.00921#page=1). Status OK. Relevance: the hole's *expected type* (analytic mode) is the single most useful constraint to hand a generator, per the ablation.
- (2025) Totality pushed down to syntax: tylr's melding "completes input tiles with additional obligations such that it can be parsed into a well-formed term, with success guaranteed over all inputs", using left-to-right operator-precedence parsing — [Moon, Blinn, Porter, Omar 2025, OOPSLA, p.1](https://arxiv.org/pdf/2508.16848#page=1). Status OK. Relevance: every token-level prefix has a well-formed completion skeleton ("obligations"), which is the syntactic analogue of a typed hole.
- (2008) Sketching: "insight is communicated through a partial program, a sketch that expresses the high-level structure of an implementation but leaves holes in place of the low-level details", solved by counterexample-guided inductive synthesis (CEGIS) — [Solar-Lezama 2008, PhD thesis, p.4](https://people.csail.mit.edu/asolar/papers/thesis.pdf#page=4). Status OK. Relevance: holes as the search variables, a validator producing counterexamples — the refuted/not-refuted loop.
- (2020) Smyth: "live bidirectional evaluation, propagates examples 'backward' through partially evaluated sketches" so that ordinary assertions become hole constraints — [Lubin, Collins, Omar, Chugh 2020, ICFP, p.1](https://arxiv.org/pdf/1911.00583#page=1). Status OK. Relevance: constraints flowing *into* holes from evaluation, complementing types flowing in from bidirectional checking.

### Inferences
- The expected type at a hole is the analytic-mode input of bidirectional typing (KQ5); Blinn et al.'s ablation is empirical evidence that this is the highest-value constraint to expose to a generator, with "headers" (in-scope values of relevant type) second.
- Totality (marking) plus indeterminate evaluation together give a generator a checker that *never blocks*: an ill-typed partial program is marked, not rejected, and can still be run to produce partial evidence.
- The reported gains are on five small programs; they establish direction, not magnitude at scale.

## KQ5. Bidirectional typing and incremental / co-contextual checking: left-to-right constraint flow and per-edit cost

### Takeaway
Bidirectional typing's *checking* mode lets an expected type flow into a subterm before the subterm exists (hence left-to-right constraint flow) and "support[s] features for which inference is undecidable"; mode-correctness forbids guessing. Co-contextual typing (Erdweg et al. 2015) inverts the context into *requirements emitted upward*, so independent subterms check bottom-up and incrementally; derived incremental checkers reach 147× (Statix/scope graphs, 2022) and multiple orders of magnitude on edits (Datalog 2020; Hazel's order-maintenance 2025). For token-level generation, prefix automata with a type-inhabitation search (Mündler et al., PLDI 2025) and coinductive realizability (ChopChop, POPL 2026) decide "can this prefix still be completed to a well-typed program?", halving compilation errors.

### Cited Findings
- (2021) Survey: "Using checking enables bidirectional typing to support features for which inference is undecidable; using synthesis enables bidirectional typing to avoid the large annotation burden of explicitly typed languages. In addition, bidirectional typing improves error locality" — [Dunfield & Krishnaswami 2021, ACM CSUR, p.1](https://arxiv.org/pdf/1908.05839#page=1); mode-correctness: "We want to avoid having to guess types: in an ideal world, whenever we synthesize a type, the type should come from known information—rather than, say, enumerating all possible types" — [same, p.4](https://arxiv.org/pdf/1908.05839#page=4); the "Pfenning recipe" makes the annotation discipline decidable from a subterm's form and its parent alone. Status OK. Relevance: checking mode is the mechanism by which a hole receives its constraint; mode-correctness is the guarantee that the checker never needs to search.
- (2000) Local type inference: "missing annotations are recovered using only information from adjacent nodes in the syntax tree, without long-distance constraints such as unification variables" — [Pierce & Turner 2000, TOPLAS, p.1](https://www.cis.upenn.edu/~bcpierce/papers/lti-toplas.pdf#page=1). Status OK. Relevance: locality is what makes per-hole checking cheap and independent of the unwritten rest of the program.
- (2015) Co-contextual typing: "We propose a co-contextual formulation of type rules that only take an expression as input and produce a type and a set of context requirements. Co-contextual type checkers traverse an expression tree bottom-up and merge context requirements of independently checked subexpressions"; "co-contextual type checking has performance comparable to standard context-based type checking, and incrementalization can improve performance significantly" — [Erdweg, Bračevac, Kuci, Krebs, Mezini 2015, OOPSLA, p.1](https://www.informatik.uni-marburg.de/~seba/publications/cocontextual-type-checking.pdf#page=1). Status OK. Relevance: "requirements as output" is precisely the shape of a verdict about a *prefix*: constraints on what the suffix must provide.
- (2017) Extended to class tables: "We prove the equivalence of FJ's type system and our co-contextual formulation. Based on our formulation, we implemented an incremental FJ type checker and compared its performance against javac" — [Kuci, Erdweg, Bračevac, Bejleri, Mezini 2017, ECOOP, p.1](https://arxiv.org/pdf/1705.05828#page=1). Status OK. Relevance: an equivalence proof between the incremental and the canonical formulation is the "cheaper checker agrees with the reference" theorem instantiated for type checking.
- (2020) Incremental checkers derived mechanically: "Our approach is based on compiling inference rules to Datalog, a carefully limited logic programming language for which incremental solvers exist" — [Pacak, Erdweg, Szabó 2020, OOPSLA, p.1](https://www.pl.informatik.uni-mainz.de/files/2020/10/incremental-typing-foundations.pdf#page=1) (author-hosted PDF; ACM blocked); the evaluation reports "multiple orders of magnitude speedups" on some change kinds and slowdowns on others. Status OK. Relevance: incremental cost is change-kind dependent; not every edit is cheap.
- (2022) Statix/scope graphs: "we achieve speedups up to 147x on synthetic benchmarks, and up to 21x on real-world projects, with initial overheads below 10%" compared with non-incremental parallel execution — [Zwaan, van Antwerpen, Visser 2022, OOPSLA, p.2](https://pure.tudelft.nl/ws/portalfiles/portal/142378366/3563303.pdf#page=2) (TU Delft Pure mirror; ACM and research.tudelft.nl copies blocked). Status OK.
- (2025) Incremental bidirectional typing in Hazel: the goal is to "incrementally update the collected type information, at a computational cost proportional to the number of potentially affected locations" — [Porter, Kirisame, Wei, Panchekha, Omar 2025, OOPSLA, p.1](https://arxiv.org/pdf/2504.08946#page=1); on the synthesized edit trace "incrementality provid[es] one or more orders of magnitude of speedup" with multi-modal bands indicating "a fundamental algorithmic speedup: while the from-scratch analysis grows linearly in program size" the incremental cost does not — [same, p.21](https://arxiv.org/pdf/2504.08946#page=21). The calculus (MALC) extends the marked lambda calculus with expected/inferred type annotations and uses order-maintenance structures from browser layout engines. Status OK. Relevance: the direct per-edit re-check cost model for a hole-by-hole generator built on bidirectional typing with total marking.
- (2025) Type-constrained decoding: "We develop a sound algorithm to determine if a partial program can be completed into a well-typed program. This algorithm is based on a novel non-deterministic automaton we construct. The automaton incrementally builds abstract syntax trees described by the partial program and annotates them with type-relevant context"; a "search over inhabitable types" handles the type-inhabitation question; results: "it reduces compilation errors by more than half and increases functional correctness relatively by 3.5% to 5.5%" and repair "by 37% on average" — [Mündler, He, Wang, Sen, Song, Vechev 2025, PLDI, p.2](https://arxiv.org/pdf/2504.09246#page=2). Status OK. Relevance: a *prefix* verdict that is sound in one direction (if the automaton rejects, no completion exists); acceptance means "not yet refuted". This is the three-valued verdict on prefixes, implemented.
- (2026) ChopChop generalizes to semantic properties: it "introduces a principled way to construct constrained decoders based on analyzing the space of programs a prefix represents. It formulates this analysis as a realizability problem which is solved via coinduction", demonstrated for equivalence to a reference program and for type safety, "while maintaining practical decoding latency" — [Nagy, Zhou, Polikarpova, D'Antoni, POPL 2026 (arXiv v2 Dec 2025), p.1](https://arxiv.org/pdf/2509.00360#page=1). Status OK. Relevance: "realizability of a prefix" is exactly the question a budgeted checker must answer for a hole; coinduction is how they make "not yet refuted" sound for unbounded completions.
- (2023) Monitor-guided decoding: "by monitoring for type-consistent object dereferences, MGD consistently improves compilation rates and agreement with ground truth"; a 1.1B model with MGD beats larger unguided models on compilation rate — [Agrawal, Kanade, Goyal, Lahiri, Rajamani 2023, NeurIPS, p.1](https://arxiv.org/pdf/2306.10763#page=1). Status OK. Relevance: a cheap static-analysis monitor as a hard per-token mask; shows the cheap/incremental end of the spectrum pays off even without a full checker.

### Inferences
- Bidirectional checking mode + co-contextual requirements together give a complete picture of left-to-right constraint flow: what is *known* flows down into the hole (expected type), what is *owed* flows up and right (requirements on the suffix). A prefix checker for disp should emit both.
- Mündler's and ChopChop's prefix analyses are two-valued at the implementation level (mask or not) but three-valued semantically (refuted / not-yet-refuted / proven only at termination). Making the "not yet" explicit, with a budget, is the gap disp targets.
- Incremental speedups are real but edit-kind dependent (Pacak); the Hazel 2025 result suggests bidirectional + total marking is the combination that makes per-edit cost local.

### Gaps
- Per-token latency figures for Mündler et al. and ChopChop were not extracted (both papers contain runtime analyses; not quoted here).

## KQ6. Three-valued or evidence-carrying verdicts; "a cheaper checker must agree with the canonical one"

### Takeaway
Kleene's third value is the standard formalization of "unknown" in static analysis (3-valued logical structures with 1/2, related to the 2-valued world by an Embedding Theorem), in model checking of partial state spaces (⊥ = "unknown whether true or false"), and in runtime verification (LTL3: true/false/inconclusive on finite prefixes, anchored to the infinite-trace semantics, with monitors deciding "as early as possible"). Bounded model checking gives "no counterexample of length ≤ k", made complete by a completeness threshold; SMT-LIB standardizes `unknown` as "the search was inconclusive — because of resource limits, solver incompleteness, or other reasons". Refinement types buy decidability by restricting refinements to decidable logics (QF-UFLIA) and refinement reflection keeps SMT decidable where axioms would not. Step-indexed types (Appel & McAllester 2001; Ahmed 2006) formalize "behaves as τ for k steps" — the exact meaning of "no counterexample within budget". The general "cheaper checker agrees with reference" theorem is abstract interpretation's soundness relation σ (Cousot); "soundiness" names the common practice of deliberately giving it up.

### Cited Findings
- (2002) 3-valued logic in abstract interpretation: "Kleene's logic has a third truth value that signifies 'unknown,' which is useful for shape analysis because we only have partial information about the actual stores" — [Sagiv, Reps, Wilhelm 2002, TOPLAS, p.3](https://www.cs.tau.ac.il/~msagiv/toplas02.pdf#page=3); "2-valued logical structures are used to encode concrete stores; 3-valued logical structures are used to encode abstract stores", with values 0, 1 definite and 1/2 indefinite under an information order, and an Embedding Theorem "to ensure that the meaning of a formula in the 'blurred' (3-valued) world is compatible with the formula's meaning in the original (2-valued) world" — [same, p.7](https://www.cs.tau.ac.il/~msagiv/toplas02.pdf#page=7). Status OK (author-hosted copy; the Wisconsin copies are scans without a text layer). Relevance: the verdict lattice {0, 1/2, 1} with information order, and the theorem relating the cheap 3-valued evaluation to the exact 2-valued one, is the template for disp's {refuted, unknown, proven}.
- (1999) Partial state spaces: "We represent incomplete state spaces as partial Kripke structures, and give a 3-valued interpretation to modal logic formulas on these structures. The third truth value ⊥ means 'unknown whether true or false'", with a completeness preorder characterized logically — [Bruns & Godefroid 1999, CAV, p.1](https://patricegodefroid.github.io/public_psfiles/cav99.pdf#page=1). Status OK. Relevance: a "possibly" answer from a model checker over an incomplete model; refining the model (more budget) moves verdicts up the information order.
- (2011) Runtime verification on finite prefixes: "It introduces a three-valued semantics (with truth values true, false, inconclusive) as an adequate interpretation as to whether a partial observation of a running system meets an LTL or TLTL property"; the monitor construction is optimal in that "the monitor identifies a continuously monitored trace as either satisfying or falsifying a property as early as possible" — [Bauer, Leucker, Schallhart 2011, TOSEM, p.1](https://cs.uwaterloo.ca/~bbonakda/teaching/CS745/papers/RV.pdf#page=1). Status OK. Relevance: the finite-prefix verdict is defined *relative to* the canonical infinite-trace semantics (true iff every extension satisfies, false iff none does, else inconclusive) — the cleanest existing theory of "a verdict on a prefix that must agree with the reference semantics", and "as early as possible" is the budget-efficiency criterion.
- (1999) Bounded model checking: "The basic idea is to consider counterexamples of a particular length k and generate a propositional formula that is satisfiable iff such a counterexample exists" — [Biere, Cimatti, Clarke, Zhu 1999, TACAS, p.5](http://www.cs.cmu.edu/~emc/15-820A/reading/biere99symbolic.pdf#page=5). Status OK. Relevance: "no counterexample within budget k" as a first-class, sound-for-refutation verdict.
- (2004) When budget suffices: "For every finite model M and an LTL property φ, there exists a number CT (the Completeness Threshold) such that if there is no counterexample to φ in M of length CT or less, then M ⊨ φ" — [Clarke, Kroening, Ouaknine, Strichman 2004, VMCAI, p.1](http://www.kroening.com/papers/vmcai2004.pdf#page=1). Status OK. Relevance: the theory of when "no counterexample within budget" upgrades to "proven"; exists for finite systems, and the paper shows computing the exact threshold is as hard as model checking, so over-approximations are used.
- (2021) SMT-LIB standardizes the don't-know verdict: `check-sat` yields "an unknown response that the search was inconclusive—because of resource limits, solver incompleteness, or other reasons" — [SMT-LIB Standard 2.6, p.65](https://smt-lib.org/papers/smt-lib-reference-v2.6-r2021-05-12.pdf#page=65), with a `:reason-unknown` info value whose grammar is "memout | incomplete | ⟨s_expr⟩" — [same, p.48](https://smt-lib.org/papers/smt-lib-reference-v2.6-r2021-05-12.pdf#page=48). Status OK. Relevance: industrial precedent for a three-valued verdict that *also carries a reason* (resource vs. incompleteness), which a budgeted checker should mirror.
- (2008) Liquid types trade expressiveness for decidability: "In our system, type checking and inference are decidable for three reasons … First, we use a conservative but decidable notion of subtyping, where we reduce the subtyping of arbitrary dependent types to a set of implication checks over base types"; refinements are conjunctions of logical qualifiers — [Rondon, Kawaguchi, Jhala 2008, PLDI, p.1](https://ranjitjhala.github.io/static/liquid_types.pdf#page=1). Status OK.
- (2020) The rule stated plainly: "Refinements are predicates drawn from decidable logics" — the quantifier-free fragment of linear arithmetic and uninterpreted functions (QF-UFLIA) — [Jhala & Vazou 2020, "Refinement Types: A Tutorial", p.5](https://arxiv.org/pdf/2010.07763#page=5). Status OK. Relevance: the decidability trade-off is a *syntactic restriction on what a type may say*; disp instead keeps types unrestricted and bounds the *checker*.
- (2018) Refinement reflection keeps SMT decidable where axioms would not: "The automation offered by axioms is a bit of a devil's bargain, as axioms render VC checking undecidable, and in practice automatic axiom instantiation can easily lead to infinite 'matching loops'" — [Vazou, Tondwalkar, Choudhury, Scott, Newton, Wadler, Jhala 2018, POPL, p.8](https://arxiv.org/pdf/1711.03842#page=8); reflecting a function's definition into its refinement type instead "permits decidable verification", and Proof by Logical Evaluation (PLE) unfolds definitions in a bounded, terminating way. Status OK. Relevance: PLE is a *budgeted unfolding* that stays complete for a class of terminating functions — a published cousin of "proven within budget".
- (2001) Step-indexed types are literally "τ for k steps": "type judgements that are indexed: v :_k τ intuitively means that, in any computation running for no more than k steps, the value v behaves as if it were an element of the type τ" — [Appel & McAllester 2001, TOPLAS, p.3](https://www.cs.princeton.edu/~appel/papers/indexed.pdf#page=3). Status OK. Relevance: the semantic meaning of a budgeted check already exists as a standard model construction; "proven" is ∀k, "no counterexample within budget k" is v :_k τ, and refutation at any k is definitive because the relation is downward closed in k.
- (2006) Same idea as a relation: "(k, v, v′) ∈ R_V⟦τ⟧ says that in any computation running for no more than k steps, v approximates v′ at the type τ" — [Ahmed 2006, ESOP, p.4](https://www.ccs.neu.edu/home/amal/papers/lr-recquant.pdf#page=4). Status OK. Relevance: extends the k-step view to equivalence/approximation, which an optimizer that replaces one program by another under a type constraint needs.
- (1996) Abstract interpretation's agreement theorem in one line: the method consists "in a priori choosing a problem-specific abstract semantics domain D♯ and an abstract semantics S♯ … Then safety, correctness or soundness is established by proving that a soundness relation σ satisfies ∀p ∈ L : σ(S⟦p⟧, S♯⟦p⟧)" — [Cousot 1996, ACM Computing Surveys, p.1](https://cs.nyu.edu/~pmc309/publications.www/Cousot-ACM-Computing-Surveys-v28-n2-p324-328-1996.pdf#page=1). Status OK (the Cousot & Cousot POPL 1977 PDF was fetched but is a scan without a text layer, so the 1996 survey is cited instead). Relevance: this is the general form of "a cheaper checker must agree with the canonical one": a relation σ between the reference semantics and the cheap one, proved for every program.
- (2015) The practice of giving σ up has a name: "virtually all published whole-program analyses are unsound and omit conservative handling of common language features when applied to real programming languages" — [soundiness.org (Livshits et al., CACM 2015 manifesto excerpt)](http://soundiness.org/#Introduction). Status OK (HTML). Relevance: a budgeted checker that returns "unknown" instead of silently assuming is the principled alternative to soundiness.

### Inferences
- Disp's three outcomes line up with existing theory one-to-one: "refuted" = BMC counterexample / LTL3 false / 3-valued 0; "no counterexample within budget" = v :_k τ / LTL3 inconclusive / SMT `unknown` with `:reason-unknown incomplete`; "proven" = ∀k / LTL3 true / completeness threshold reached. The information order on these is Kleene's; monotonicity in budget is the Embedding Theorem's direction.
- The LTL3 definition is the best template for *specifying* a prefix/budget verdict relative to a reference semantics: define the verdict by quantifying over all extensions (all larger budgets), then prove the implementation decides it as early as possible.
- A "completeness threshold" for disp exists only for finite fragments; in general the "unknown" verdict cannot be eliminated, which is the same conclusion the fire triangle reaches from the type-theoretic side.
