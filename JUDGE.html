Inside judge: where a run needs a statement

A step-through of how judge (lib/rules.disp) proves a function type for ten small definitions, and of the two places it stops and needs a fact about some other function. Each case list below was recorded from the real checker; the steps inside each case are written out from the machine's rules in lib/machine.disp and the evaluator in lib/confirm.disp, with the line that does each one.

xs.tail an input piece: one unknown argument (or a part of one), "some List(Nat), not saying which" rev(xs.tail) the hypothesis's answer: what the recursive call returns, known only by its type cat(…) a lemma's answer: a call to an already-proved function, known only by that function's type

1. Only one rule looks at its argument

The checker runs the program's tree on the machine in lib/machine.disp, the same step function that runs plain trees (m_rule, line 72). The evaluator in lib/confirm.disp (sapply_from, line 469) adds one thing: an application that would read an unknown value's shape is held back from the rules and answered separately (held, line 426). Four of the five rules only build, drop or copy the argument. Only the triage rule asks for its shape, so every is_leaf, is_zero, .fst and if on data ends up there.

2. A stream is a tree

Both checkers below read a stream, and in disp a stream is an ordinary tree: a step function and a state, paired (lib/stream.disp). Nothing runs until something pulls it. A pull, c_out, runs the step function on the state once; what comes back says what the stream emitted and holds the next stream, which is the same pair with the new state.

c_new :: {fmap : (X -> Y) -> F(X) -> F(Y), stepper : St -> F(St), state : St} -> Coalgebra(F) :=> pair(fmap, pair(stepper, state))
c_out :: {c : Coalgebra(F)} -> F(Coalgebra(F)) :=> c.c_fmap(c_with(c), c.c_stepper(c.c_state))
s_new :: {stepper : St -> Step(Ending, Emit(Option(V), St)), state : St} -> Items(V) :=> c_new(item_map, stepper, state)

A stream of possible counterexamples is decided by verdict: pull until something is yielded (Refuted, with it) or the stream ends (Exhausted: Proved; Spent: Open, with the reason). Two different streams feed it on this page.

verdict :: {witnesses : Bounded(Items(Tree))} -> Verdict :=> c_fold({recurse, step} =>
	if (step.is_finished) { ending_verdict(step.finished_result) }
	else if (step.step_draw.is_yield) { refuted(step.step_draw.yielded_item) }
	else { recurse(step.step_rest) }
, witnesses)

// brute force (lib/claim.disp): every tree, smallest first; keep the ones the program fails
honest :: {source : Items(Tree), claim : Claim, w : Tree, budget : Nat} -> Verdict :=>
	verdict(source.s_filter({c} => not(claim(w, c))).bounded(budget))

// what judge runs (lib/confirm.disp): a work list of cases, read for its counterexamples
search_steps :: {checks : List(Val -> Res), ground : Val -> Option(Tree), instances : Val -> List(Val), start : List(Pair(Val, Nat))} -> Items(Step) :=>
	s_steps(settle_case(checks, ground, instances), start)
// (lib/stream.disp) what a work list yielded
s_yielded :: {steps : Items(Pair(I, Outcome(V, I)))} -> Items(V) :=> steps.s_filter({step} => step.snd.is_yield).s_map({step} => step.snd.yielded_item)
steps_verdict :: {steps : Items(Step)} -> Verdict :=>
	verdict(s_yielded(steps))
search_g :: {checks : List(Val -> Res), ground : Val -> Option(Tree), instances : Val -> List(Val), input : Val, depth : Nat} -> Verdict :=>
	steps_verdict(search_steps(checks, ground, instances, [pair(input, depth)]))

s_filter and bounded do not run anything either: each builds a new stream whose step function calls the old one and rewrites what it emitted (a kept item becomes a skip; the last unit of fuel becomes the end). The work list is a stream whose state is a pair: the cases still to do, and the reasons noted so far.

s_steps :: {settle : I -> Outcome(V, I), start : List(I)} -> Items(Pair(I, Outcome(V, I))) :=> s_new({st} => {
	let todo := st.fst
	let notes := st.snd
	if (todo.is_nil) { finished(if (notes.is_nil) { exhausted } else { spent_on(notes.head) }) }
	else {
		let out := settle(todo.head)
		let rest := if (out.fst == "Split") { pair(out.snd.snd.append(todo.tail), notes) }
			else if ((out.fst == "Noted") && (notes.is_nil)) { pair(todo.tail, [out.snd]) }
			else { pair(todo.tail, notes) }
		running(emit(yield(pair(todo.head, out)), rest))
	}
}, pair(start, []))

So the "work list" in the next section is not a separate structure: it is this state, and each case in the case tree is one pull. The stream yields every case with what settled it; s_yielded keeps only the counterexamples, so to verdict a settled case is a skip. The settle function is settle_case; an item is a pair of the case's arguments and the splits left. The same list read back as data is derivation (lib/rules.disp, line 279).

3. Step through a proof

Pick a definition. Step walks the run of the next case; the last step of each case is one pull of the work-list stream, which settles the case with settle_case (lib/confirm.disp:644). Every case is run exactly first. Where definitions already Proved are given as lemmas and that run does not settle the case, it is run again with them read by their types. A case a run answers Yes for is done for every input it stands for, and the Yes says what it rests on besides the run: the hypothesis (induction), a lemma; a case whose run needs an input piece's shape is split into that type's cases; a stuck run is noted and makes the verdict Open; a known input that fails is a counterexample and ends the search.

    5. Where the statement comes in

    Run the ten definitions and the pattern is short.

    • Splitting loses nothing. An input piece stands for exactly the members of its type, and its cases (one per shape the type allows) cover the same members. So splitting is brute force with the inputs grouped, and it works on raw programs. dup is refuted that way; next never even splits.
    • The hypothesis forgets. For a recursive definition the call on a smaller piece is answered by the hypothesis: some member of the result type, nothing more. That is fine while the program only wraps the answer (twice puts succ around it, cat puts cons around it). It is not an input, so it has no cases to split.
    • Need 1: someone looks at the hypothesis's answer. In rev, cat runs is_leaf on rev(xs.tail) at once. The strip shows why nothing could answer: across inputs, rev(xs.tail) is sometimes [] and sometimes not. The run is stuck, at any budget.
    • Need 2: a recursion with no hypothesis. In wrap nothing is forgotten, but cat's recursion is not the function being judged, so it gets no hypothesis. Every split exposes another tail to split. The cases it closes are one list length each, which is brute force again, and the split budget runs out.
    • Both need the same thing: a statement about cat, proved by cat's own induction (the cat run), then used as a lemma: when a run of cat stops, the lemma answers "some List(Nat)" if the arguments are in cat's domain. rev and wrap with the lemma are Proved.
    • A lemma hides nothing. A lemma's answer forgets what cat computes, so every case is run exactly before any lemma is read by its type, and a check that reads by type never refutes. bug is refuted by the input [], and with the lemma it still is (lib/confirm.disp:644).
    • When the statement need not be written. Before giving up, the checker tries each recursive definition inside the value at the function types the goal's own type is built from (lib/rules.disp:202). times : Nat -> Nat -> Nat calls an unannotated plus and is Proved that way (lib/theories/checked_example.disp). rev is not: cat's type has two list arguments, and List(Nat) -> List(Nat) is not built from it. That is the place the annotation is needed.

    Why not split the hypothesis's answer as if it were an input? Splitting it would be sound, since every list is [] or a cons. But cat would then recurse on the tail of that answer, with no hypothesis of its own: that is the wrap situation. Either way the missing piece is an induction on cat, and its statement is what the annotation on cat supplies. (The checker does not try this; the paragraph is the reason it would not help.)
