# Compute-aware and modular type theories: cost as part of the judgment, budgeted checking, and type theories as data

Scope note for the report writer. The system being compared is disp: a dependently typed language on Barry Jay's tree calculus (a reflective combinator calculus where programs can inspect programs). In disp a type is an ordinary program that answers yes or no about a value; type checking runs as a stream of cheap steps under a step budget and ends in "refuted with a witness", "no counterexample within budget", or "proven"; fast checkers are shortcuts that must agree with the slow canonical stream; the checker is itself a program to be optimized and swapped; the end goal is an optimizer that searches programs under the type as a constraint.

Research done 2026-10-09. Every linked source below was fetch-verified with `scripts/verify-source.sh -q '<quote>' <url|doi|arxiv>`; the link given is the fragment the script minted (`#page=N` for PDFs, `#anchor` for HTML, or the bare page when no anchor preceded the match). Quotes are verbatim from the fetched text (PDF-to-text may drop ligatures). Sources that could not be fetched are listed in the final section and are NOT linked in the body. "As of" dates refer to the version fetched on 2026-10-09.

## Q1. Cost-aware type theory: calf (POPL 2022) and decalf (POPL 2024). Which judgments carry cost, and how are extensional and intensional reasoning separated?

### Takeaway
calf does not put a budget in the typing judgment. It puts cost into the *term language* as a computational effect (`step`), and separates behaviour from cost with a modal "phase distinction": under the extensional phase all cost annotations are erased, so a proposition about behaviour cannot see cost (an internal noninterference theorem). decalf (2024) drops the separable cost effect and instead makes every type carry an intrinsic preorder; "a cost bound is simply another program" and the ordering collapses to extensional equality in the behavioural phase. Follow-ups in 2024–2025 added domain-theoretic adequacy for a cost-aware PCF and proved calf's canonicity. The metatheory kept is full dependent type theory plus noninterference; what is NOT there is any notion of "the checker ran out of fuel": calf is a framework for *proving* cost bounds, not a budgeted checker.

### Cited Findings
- calf's design statement (arXiv v2, Oct 2021; POPL 2022): "we argue that the cost structure of programs motivates a phase distinction between intension and extension. Armed with this technology, we contribute a synthetic account of cost structure as a computational effect in which cost-aware programs enjoy an internal noninterference property: input/output behavior cannot depend on cost. As a full-spectrum dependent type theory, calf presents a unified language for programming and specification of both cost and behavior" — [Niu, Sterling, Grodin, Harper, "A cost-aware logical framework", arXiv:2107.04663, p.1](https://arxiv.org/pdf/2107.04663#page=1)
- The reference implementation is an Agda library: "**calf**: A Cost-Aware Logical Framework" — [jonsterling/agda-calf README](https://github.com/jonsterling/agda-calf#calf-a-cost-aware-logical-framework) (fetched 2026-10-09).
- decalf (POPL 2024) keeps the phase distinction but changes how cost is represented: "Like Calf, the language is based on an internal phase distinction between the behavior of a program and its cost measured by an effect. Decalf extends Calf by accommodating other effects, such as probabilistic choice, which requires a reformulation of Calf's approach to cost analysis: rather than rely on a separable notion of cost, here a cost bound is simply another program. Formally, every type is equipped with an intrinsic preorder, allowing effectful programs to be compared for cost inequality." — [Grodin, Niu, Sterling, Harper, "Decalf", arXiv:2307.05938, p.1](https://arxiv.org/pdf/2307.05938#page=1)
- decalf's separation of intension and extension is a *restriction of an ordering*: the type system "is based on an intrinsic cost ordering among terms that restricts in the behavioral phase to extensional equality"; it is "semantically justified via a model in the topos of augmented simplicial sets." — [decalf, arXiv:2307.05938, p.1](https://arxiv.org/pdf/2307.05938#page=1). Semantic Scholar lists the published version as Proc. ACM Program. Lang. 2024, doi:10.1145/3632852.
- Cost-sensitive adequacy (MFPS 2024, arXiv Mar 2024): "We study a cost-aware programming language for higher-order recursion dubbed PCFcost in the setting of synthetic domain theory (SDT). Our main contribution relates the denotational cost semantics of PCFcost to its computational cost semantics" — [Niu, Sterling, Harper, arXiv:2404.00212, p.1](https://arxiv.org/pdf/2404.00212#page=1). The script also matched "noninterference" on pp.4–5 of this paper.
- Canonicity for calf (arXiv Apr 2025): "In the original work on the cost-aware logical framework by Niu et al. [28], a dependent variant of the call-by-push-value language for cost analysis, the authors conjectured that the canonicity property of the type theory can be succinctly proved via Sterling's synthetic Tait computability. This work resolves the conjecture affirmatively." — [Li & Harper, arXiv:2504.12464, p.1](https://arxiv.org/pdf/2504.12464#page=1)

### Inferences
- In calf/decalf "cost" is a *proposition proved inside the theory about a program*, never a *budget consumed by the checker*. For disp the mapping is: calf's `step` effect ~ disp's step counter; calf's extensional phase ~ disp's "the answer a type gives must not depend on how many steps were spent getting it". The noninterference theorem is exactly the property disp wants between a fast checker and the canonical stream: behaviour (accept/refute) must be invariant under cost.
- decalf's "a cost bound is simply another program" is the same move disp makes with "a type is a program": both make the specification object a term of the same language, so the optimizer can search over cost bounds as it searches over programs.
- Nothing in this lineage gives a semantics for a *third* answer ("no counterexample within budget"). Their judgments are two-valued; a budget-exhausted outcome has to be modelled elsewhere (see Q3, Q5).

### Gaps
- I found no calf/decalf paper that treats the type checker's own running time; cost is only about object programs. (Searched "cost-aware type theory 2025 Niu Harper phase distinction"; results were the 2024 adequacy paper and the 2025 canonicity paper.)
- A 2025 item "A Verified Cost Analysis of Joinable Red-Black Trees" (Grodin, Li, Harper) appeared only in a search snippet; not fetched or verified.

## Q2. Graded and quantitative types: QTT (Atkey 2018), Granule (2019), graded modal dependent type theory (2021), Resource-Aware ML. How do grades parameterize typing, and what can they not express?

### Takeaway
Grades annotate *variables in a context* with elements of a semiring and the rules add/multiply them; the semiring is the parameter. QTT's key trick is that grade 0 means "erased at run time but still usable in types", which is a static intension/extension split. Granule generalizes to arbitrary semirings and discharges constraints with SMT. GrTT (2021) puts grades on dependent types and uses them to *speed up the type checker itself*. RaML is the opposite style: no grades in source types; a linear-programming inference finds polynomial resource bounds automatically. None of these systems make the checker's budget a parameter: grades bound *resource use of the program*, are decided by solvers (SMT/LP) that are themselves unbounded, and cannot express data-dependent or non-polynomial costs without leaving the fragment.

### Cited Findings
- QTT: "We present Quantitative Type Theory, a Type Theory that records usage information for each variable in a judgement, based on a previous system by McBride. The usage information is used to give a realizability semantics using a variant of Linear Combinatory Algebras" — [Atkey, "Syntax and Semantics of Quantitative Type Theory", LICS 2018, author PDF p.1](https://bentnib.org/quantitative-type-theory.pdf#page=1)
- The 0-grade erasure idea (same paper): McBride's "insight is to use the 0 of the semiring to represent information that is erased at runtime, but is still available for use in types (i.e., extensionally)." — [Atkey 2018, author PDF](https://bentnib.org/quantitative-type-theory.pdf#page=1) (passage is in the introduction; the minted fragment is for the abstract).
- Granule (ICFP 2019) frames grades as a *family* parameterized by a semiring: recent work generalised BLL "providing a family of modalities whose indices are drawn from an arbitrary semiring, enabling various properties to be tracked by a single system, e.g., bounded reuse, strictness, deconstructor use, sensitivity, and scheduling constraints in hardware synthesis"; "We propose the general terminology of graded modal types"; demonstrated "in a fully-fledged functional language called Granule." — [Orchard, Liepelt, Eades, "Quantitative Program Reasoning with Graded Modal Types", author PDF p.1](https://www.cs.kent.ac.uk/people/staff/dao7/publ/granule-icfp19.pdf#page=1)
- Granule project self-description (site fetched 2026-10-09): the project aims "to capture more and more intensional properties of programs at the type-level, that is, how a program computes not just what it computes. Our primary mechanism for doing this is via the relatively new notion of graded types in concert with other typing mechanisms like linear types and dependent types." — [granule-project.github.io](https://granule-project.github.io/)
- GrTT (ESOP 2021): the paper reports "an application of grading to optimising the type checking procedure itself." — [Moon, Eades, Orchard, "Graded Modal Dependent Type Theory", arXiv:2010.13163, p.1](https://arxiv.org/pdf/2010.13163#page=1)
- RaML (POPL 2017): the system "automatically derives worst-case resource bounds"; "Bound inference is fully automatic and reduced to a linear optimization problem that is passed to an off-the-shelf LP solver. Technically, the analysis system is based on a novel multivariate automatic amortized resource analysis (AARA)." — [Hoffmann, Das, Weng, "Towards Automatic Resource Bound Analysis for OCaml", arXiv:1611.00692, p.1](https://arxiv.org/pdf/1611.00692#page=1)

### Inferences
- The "semiring as parameter" design is the closest existing analogue of a *swappable* resource discipline: you change what the checker tracks by changing an algebra, not the rules. For disp, the equivalent would be a step-count semiring (ℕ with + and max, or ℕ with + and ×) attached to the checking stream, but note that in all these systems the grade is computed statically by a solver and never represents "steps the checker actually spent".
- Atkey's 0-grade is a *syntactic* intension/extension split (what runs vs. what is only reasoned about), complementary to calf's *modal* one. A disp type that inspects a value's structure (intensional) would be grade-ω in the type position; the zero grade cannot describe it.
- GrTT is, as of 2021, the only paper in this cluster where grades make the *checker* cheaper (by skipping substitution into unused positions), which is one form of "cheap checker that agrees with the canonical one": the optimization is justified by the typing derivation, not by a separate agreement proof.

### Gaps
- I did not fetch Hoffmann & Jost's "Two decades of automatic amortized resource analysis" (MSCS 2022; Cambridge Core likely blocks), so the limits of AARA (polynomial only, no logs, no non-amortizable patterns) are stated from the RaML paper's own description of its fragment, not from a survey.
- Expressiveness limits of graded systems (e.g., no dependency of grades on run-time values without full dependent grades) are my reading of the semiring design; I found no single primary source that lists them.

## Q3. Step-indexing and fuel: step-indexed logical relations, guarded/clocked type theory, fuel-based termination in Rocq/Lean and Agda. How does a step budget appear in semantics and what approximation does it yield?

### Takeaway
There are three distinct "budget" devices and they approximate differently. (1) Step-indexed models: `v :k τ` means "behaves like τ for k steps"; membership is monotone downward in k, so a finite k gives a *sound under-approximation of the type* that converges to the real type as k→∞. (2) Guarded/clocked type theory internalizes the index as a `later` modality so productivity is a typing fact, with clocks to get coinductive types back. (3) Fuel/partiality monads (Capretta's delay monad, McBride's free-monad reading) move general recursion into a total language: a function returns a *stream of steps*, and running it with fuel n yields "value" or "not yet". Agda's `NON_TERMINATING` pragma is the practical form: the definition runs at run time but is never unfolded by the checker. Cayenne (1998) is the earliest dependently typed checker that literally had a reduction-step cap with a "gave up" outcome.

### Cited Findings
- Step indexing, original definition: "Our new semantics is a term model, with type judgements that are indexed: v :k τ intuitively means that, in any computation running for no more than k steps, the value v behaves as if it were an element of the type τ. The recursive types of interest are well founded in the sense that in order to determine whether v :k τ it suffices to know whether w :j τ for all values w and j < k." and "Note that if e :k τ and 0 ≤ j ≤ k then e :j τ." — [Appel & McAllester, "An Indexed Model of Recursive Types for Foundational Proof-Carrying Code", Princeton TR-629-00 (Nov 2000; TOPLAS 2001), p.1](https://www.cs.princeton.edu/techreports/2000/629.pdf#page=1)
- Guarded dependent type theory (FoSSaCS 2016): gDTT is "an extensional dependent type theory with a 'later' modality and clock quantifiers for programming and proving with guarded recursive and coinductive types. The later modality is used to ensure the productivity of recursive definitions in a modular, type based, way. Clock quantifiers are used for controlled elimination of the later modality and for encoding coinductive types using guarded recursive types." — [Bizjak, Grathwohl, Clouston, Møgelberg, Birkedal, arXiv:1601.01586, p.1](https://arxiv.org/pdf/1601.01586#page=1)
- Partiality as a monad (LMCS 2005): Capretta's paper has a section "8. Partiality as a monad" and contrasts with the Bove–Capretta method, which "allows the definition of partial functions by restricting them to their domain of convergence." — [Capretta, "General recursion via coinductive types", LMCS 1(2:1) 2005, p.1](https://lmcs.episciences.org/2265/pdf#page=1) (the "partial/delay" matches were on pp.1, 3, 5).
- Free-monad reading of general recursion (2015): "general recursive definitions can be represented in the free monad which supports the 'effect' of making a recursive call, without saying how these calls should be executed. Diverse semantics can be given within a total framework by suitable monad morphisms." and "To make a weaker promise, simply construct a total function of type S → G T where G is a suitable monad." — [McBride, "Turing-Completeness Totally Free", author PDF p.1](https://personal.cis.strath.ac.uk/conor.mcbride/TotallyFree.pdf#page=1)
- Agda's practical split (docs for Agda 2.9.0, fetched 2026-10-09): "The NON_TERMINATING pragma. This is a safer version of TERMINATING which doesn't treat the affected functions as terminating. This means that NON_TERMINATING functions do not reduce during type checking. Though, they do reduce at run-time" — [Agda docs, Termination Checking](https://agda.readthedocs.io/en/latest/language/termination-checking.html#non-terminating-pragma)
- Cayenne (1998) — a dependently typed checker with an explicit step cap: "this power comes at a cost: type checking of Cayenne is undecidable. While this may appear to be a steep price to pay, it seems to work well in practice." — [Augustsson, "Cayenne — a language with dependent types", p.1](https://www.cs.tufts.edu/~nr/cs257/archive/lennart-augustsson/cayenne.pdf#page=1). Section 4.4 of the same PDF: "Having undecidable type checking means that the type checker might loop. This is clearly not a user friendly type checker. So instead the implemented type checker has an upper bound on the number of reduction steps that it may perform. If this limit is exceeded the type checker will report this." and "Very infrequently does the type checker report that it did not terminate within the prescribed number of steps. Most often, this is the result of a type error, but sometimes the type expression is just too complicated and the number of reduction steps must be increased (the number of reduction steps is a compiler flag)." — [same PDF, §4.4](https://www.cs.tufts.edu/~nr/cs257/archive/lennart-augustsson/cayenne.pdf)
- Approximate normalization (ICFP 2019) — keeping decidability with nontermination: "To account for nontermination and failure, we distinguish between compile-time normalization and run-time execution: compile-time normalization is approximate but total, while runtime execution is exact, but may fail or diverge. We prove that GDTL has decidable typechecking" — [Eremondi, Tanter, Garcia, "Approximate Normalization for Gradual Dependent Types", arXiv:1906.06469, p.1](https://arxiv.org/pdf/1906.06469#page=1)
- Two-fragment design (POPL 2014): Trellys/Zombie has "two fragments that share a common syntax and overlapping semantics: a logic that guarantees total correctness, and a call-by-value programming language that guarantees type safety but not termination. The two fragments may interact: ... 'mobile' program values, including proofs computed at runtime, may be used as evidence by the logic." — [Casinghino, Sjöberg, Weirich, "Combining Proofs and Programs in a Dependently Typed Language", author PDF p.1](https://www.engineering.upenn.edu/~sweirich/papers/popl14-trellys.pdf#page=1)

### Inferences
- The step-indexed `v :k τ` relation is precisely the formal object behind disp's "no counterexample within budget": if the checker has run k steps without refuting, it has established `v :k τ` for the type's *k-approximant*; monotonicity in k (Appel–McAllester's downward closure) is what makes a larger budget strictly more informative and what makes "proven" the limit. This gives an existing, well-studied answer to "what does a budget-bounded acceptance mean" — it is membership in the k-th approximant, not in the type.
- Capretta's delay monad is the type of disp's checking stream: a type-as-program that may not terminate is a total function into `Delay Bool`, and the budget is how many `later` constructors you are willing to peel. McBride's point that the *same* free-monad term can be run under several semantics (fuel, step-indexed, Bove–Capretta domain predicate) is the theoretical licence for "fast checkers are different interpreters of the same canonical stream".
- Cayenne is the direct ancestor of a budgeted checker and shows the pragmatic consequence: a three-way outcome (accept / reject / "did not terminate within the prescribed number of steps") where the third is treated as an error with a user-tunable flag. Eremondi et al. show the other option: make compile-time evaluation *approximate but total* so the checker always answers, at the cost that the static answer may be imprecise.
- Agda's `NON_TERMINATING` and Trellys' two fragments are the "don't unfold it" strategy: decidability is preserved by refusing to run possibly-looping code during checking. disp's design is instead "run it, but count".

### Gaps
- Clocked Type Theory (Bahr, Grathwohl, Møgelberg, LICS 2017) was not fetched; gDTT stands in for the guarded/clocked family.
- I did not fetch a primary source on Rocq's structural-recursion/`Fixpoint` guard or Lean's `partial`/well-founded recursion; the Agda and Cayenne sources cover the "do not unfold" and "step cap" patterns respectively. Lean's `decide +kernel` and cbv behaviour are covered under Q4.

## Q4. Checking by computation: proof by reflection, SSReflect boolean reflection, Lean `decide`/`native_decide`, Rocq `vm_compute`/`native_compute`. What are the trust and cost trade-offs when the checker just runs the program?

### Takeaway
"Reflection" means: write a boolean decision procedure `f`, prove once `f x = true → P x`, then for each instance just *run* `f`. The trade-off is where the running happens. Kernel reduction (Lean `decide`, Rocq `cbv`) keeps the trusted base at the kernel but is slow. Compiled evaluation (Rocq `vm_compute`/`native_compute`, Lean `native_decide`) is 2–5× (or far more) faster but either (a) requires a mechanically verified evaluator (Grégoire–Leroy's approach for `vm_compute`) or (b) adds the whole compiler to the trusted base and leaves an auditable axiom in the proof (Lean's per-invocation `ofReduceBool` axiom). This is exactly "cheap checker must agree with canonical checker", formalized as either a verified-evaluator theorem or an explicit trust marker.

### Cited Findings
- SSReflect (JFR 2010) tutorial abstract: the extension "focuses on the application of the small scale reflection methodology to the formalization of finite objects in intuitionistic type theory." — [Gonthier & Mahboubi, "An introduction to small scale reflection in Coq", JFR 3(2):95–152](https://jfr.unibo.it/article/view/1979)
- Lean reference (fetched 2026-10-09), `native_decide`: "native_decide is a synonym for decide +native. It will attempt to prove a goal of type p by synthesizing an instance of Decidable p and then evaluating it to isTrue. Unlike decide, this uses #eval to evaluate the decidability instance. This should be used with care because it adds the entire lean compiler to the trusted part, and a new axiom will show up in #print axioms for theorems using this method or anything that transitively depends on them. Nevertheless, because it is compiled, this can be significantly more efficient than using decide, and for very large computations this is one way to run external programs and trust the result." — [Lean Language Reference, Tactic Reference § native_decide](https://lean-lang.org/doc/reference/latest/Tactic-Proofs/Tactic-Reference/#native_decide)
- Same page on the kernel-only alternative: "The proofs produced by cbv only use the three standard axioms (propext, Quot.sound, and Classical.choice). In particular, they do not require trust in the correctness of the code generator, unlike native_decide." — [Lean Tactic Reference](https://lean-lang.org/doc/reference/latest/Tactic-Proofs/Tactic-Reference/#native_decide)
- Lean's trust marker is per-instance and auditable (fetched 2026-10-09): "proofs by native evaluation introduce a dedicated axiom for each computation that is asserted by the compiled code. These axioms track proofs that depend on the correctness of the entire compiler, and not just on the much smaller kernel." and "The native_decide tactic creates a bespoke axiom for each invocation. This allows each axiom to be audited for the precise statement that it proves." — [Lean Language Reference, Axioms](https://lean-lang.org/doc/reference/latest/Axioms/#standard-axioms)
- Rocq reference manual (9.4+alpha, fetched 2026-10-09): "vm_compute is a brute-force but efficient tactic that first normalizes the terms before comparing them. It is based on a bytecode representation of terms similar to the bytecode representation used in the ZINC virtual machine ... It is especially useful for intensive computation of algebraic values, such as numbers, and for reflection-based tactics. native_compute is based on converting the Rocq code to OCaml." "native_compute is typically two to five times faster than vm_compute at applying conversion rules when Rocq is running native code, but native_compute requires considerably more overhead." Both "add a single explicit cast to the proof term to tell the kernel which reduction engine to use." — [Rocq refman, Applying conversion rules](https://rocq-prover.org/doc/master/refman/proofs/writing-proofs/equality.html#applyingconversionrules)
- Why a verified evaluator (ICFP 2002): "Such a mechanically-checked correctness proof is required to ensure that we do not compromise the logical consistency of the Coq system by plugging a buggy evaluator in it." — [Grégoire & Leroy, "A compiled implementation of strong reduction", author PDF p.1](https://xavierleroy.org/publi/strong-reduction.pdf#page=1)
- A verified checker in the host (MetaRocq, README fetched 2026-10-09): "Safe Checker: Implementation of a fuel-free and verified reduction machine, conversion checker and type checker for PCUIC. This relies on a postulate of strong normalization of the reduction relation of PCUIC on well-typed terms. The checker is shown to be correct and complete w.r.t. the specification" — [MetaRocq/metarocq README](https://github.com/MetaRocq/metarocq)
- Certifying algorithms as the general frame for "fast untrusted computation + cheap check" (2011): "A certifying algorithm is an algorithm that produces, with each output, a certificate or witness (easy-to-verify proof) that the particular output has not been compromised by a bug. A user of a certifying algorithm inputs x, receives the output y and the certificate w, and then checks, either manually or by use of a program, that w proves that y is a correct output for input x." — [McConnell, Mehlhorn, Näher, Schweitzer, "Certifying Algorithms", author PDF p.1](https://people.mpi-inf.mpg.de/~mehlhorn/ftp/CertifyingAlgorithms.pdf#page=1)

### Inferences
- Reflection already *is* "a type is a program that answers yes or no": `Decidable p` in Lean and `reflect` in SSReflect are boolean recognizers with a one-time soundness lemma. disp's novelty relative to this is only that the recognizer may not terminate and so is run under a budget.
- "Cheap checker agrees with canonical checker" is formalized in two existing ways: (a) a *verified evaluator* (Grégoire–Leroy; MetaRocq's SafeChecker "correct and complete w.r.t. the specification"), where agreement is a theorem; (b) an *explicit trust axiom per use* (Lean `ofReduceBool`), where agreement is assumed and recorded so it can be audited or forbidden. The certifying-algorithms frame is a third: the fast checker emits a witness (for disp, a refuting counterexample or a trace) that the canonical checker can verify cheaply.
- MetaRocq's "fuel-free ... relies on a postulate of strong normalization" is a precise statement of what you must assume to drop the budget: the only way to run the canonical checker without fuel is to assume termination of reduction on well-typed terms. disp, which does not have that assumption for arbitrary tree-calculus programs, must keep fuel.

- Boutin 1997 (the original "proof by reflection" paper) is Springer-only and could not be fetched; it is listed in the unverified section with Semantic Scholar metadata.
- Agda-side "decide by evaluation" (`Dec`, `from-yes`) has no single primary document I could fetch; not cited.
- I did not verify Lean's claim of actual soundness incidents from native code generation; one cached document from another session asserts "known bugs in native code generation ... have produced proofs of False" but it was not part of this session's verification and is not cited.

## Q5. Refutation-first and bounded verification: QuickCheck/SmallCheck, bounded model checking and the small-scope hypothesis, k-induction, anytime algorithms. How are bounded "no counterexample" results stated and combined with proofs?

### Takeaway
All of these state the bounded result as "no counterexample of size/depth/length ≤ k", never as "true". BMC makes the bound the maximal counterexample length and reduces to SAT; SmallCheck makes it a value depth and increases it progressively; the small-scope hypothesis is the empirical claim that most bugs show at small bounds. The two mechanisms for turning bounded search into proof are (1) k-induction (Sheeran et al.), which combines "no counterexample in k steps" with an inductive step, and (2) completeness thresholds in BMC (a bound beyond which absence of counterexamples is proof). Anytime algorithms (Dean & Boddy 1988; Zilberstein 1996) are the general decision-theoretic frame: an interruptible computation whose result quality is a function of time spent.

### Cited Findings
- QuickCheck (ICFP 2000): "Properties are described as Haskell functions, and can be automatically tested on random input, but it is also possible to define custom test data generators." — [Claessen & Hughes, "QuickCheck", author PDF p.1](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quick.pdf#page=1)
- SmallCheck (Haskell Symposium 2008) abstract: "instead of using a sample of randomly generated values they test properties for all values up to some limiting depth, progressively increasing this limit." — [Runciman, Naylor, Lindblad, Chalmers record](https://research.chalmers.se/en/publication/111867#publication-abstract)
- SmallCheck library status (Hackage, fetched 2026-10-09): "SmallCheck is a testing library that allows to verify properties for all test cases up to some depth." The maintainers add: "As of 2023, this library is largely obsolete: arbitrary test generators with shrinking such as falsify offer much better user experience." — [hackage smallcheck](https://hackage.haskell.org/package/smallcheck#description)
- Small-scope evaluation for data structures (MIT TR-921, 2003): the hypothesis tested is "There is a certain small scope that satisfies mutation-adequacy criterion for data structures" and the result is "Exhaustive testing within small scope can generate mutation-adequate test suites." — [Marinov, Andoni, Daniliuc, Khurshid, Rinard, "An Evaluation of Exhaustive Testing for Data Structures", p.1](https://www.cs.columbia.edu/~andoni/papers/TR921.pdf#page=1)

- Bounded model checking (TACAS 1999): "The basic idea is to consider counterexamples of a particular length k and generate a propositional formula that is satisfiable iff such a counterexample exists. ### Inferences
- disp's three outcomes map directly: "refuted with a witness" = BMC/QuickCheck counterexample (BMC even gives a *minimal* one); "no counterexample within budget" = SmallCheck depth-k pass or BMC at bound k; "proven" = k-induction succeeded or a completeness threshold was reached. The literature's convention is to report the bound with the negative result and never to upgrade it silently.
- The small-scope hypothesis is the empirical justification for running the cheap refuter *first*: most type errors in disp should appear at tiny inputs, so a short budget already carries most of the refutation value.
- Zilberstein's "composition of several anytime algorithms" is the control problem disp will face when the checker is a pipeline of fast shortcuts and a slow canonical stream: which to run, for how long, and how to combine their partial answers.

## Q6. Decidability facts that bound any checker. What semi-decision is possible for a budgeted checker?

### Takeaway
Inhabitation is PSPACE-complete for simple types and undecidable for System F (via Löb's translation of first-order classical logic into second-order intuitionistic propositional logic); type checking and reconstruction for System F (Curry style) are undecidable (Wells); dependent type checking with general recursion is undecidable because conversion is β-equality, which is undecidable (Church). Consequence: a budgeted checker can be at most a *semi-decision procedure* for refutation (a counterexample, once found, is checkable) and a *co-semi-decision procedure* only on fragments where the type's recognizer is total. "Proven" for an arbitrary recognizer requires a termination argument from outside the stream.

### Cited Findings
- Simply typed inhabitation is PSPACE-complete (Statman 1979, presented in the DIKU lecture notes): "The type inhabitation problem is shown to be PSPACE-complete by a reduction from the satisfiability problem for classical second-order propositional formulas." — [Sørensen & Urzyczyn, "Lectures on the Curry-Howard Isomorphism" (1998), p.4](http://disi.unitn.it/~bernardi/RSISE11/Papers/curry-howard.pdf#page=4)
- System F inhabitation undecidable (same notes, Chapter 12): "12.3.6. Corollary. The inhabitation problem for the polymorphic lambda calculus ('Given type τ, is there a closed term of type τ?') is undecidable." and on the source of the result: "M.H. Löb [67] has published another proof of Theorem 12.2.8. The main result of [67] which implies undecidability, is an effective translation from first-order classical logic to second-order intuitionistic logic." — [Sørensen & Urzyczyn, lecture notes](http://disi.unitn.it/~bernardi/RSISE11/Papers/curry-howard.pdf#page=104) (the minted fragments for "PSPACE-complete" were pp.4, 104, 111; the Chapter 12 passages are near p.104+).
- Type checking for System F undecidable (same notes): "12.5.7. Theorem (Wells [117]). Type reconstruction and type checking in the second-order λ-calculus are recursively equivalent and undecidable." — [Sørensen & Urzyczyn, lecture notes](http://disi.unitn.it/~bernardi/RSISE11/Papers/curry-howard.pdf)
- β-equality undecidable (same notes, outline of Chapter 1): "Church's theorem stating that β-equality is undecidable." — [Sørensen & Urzyczyn, lecture notes p.4](http://disi.unitn.it/~bernardi/RSISE11/Papers/curry-howard.pdf#page=4)
- A real dependently typed checker that is undecidable: "type checking of Cayenne is undecidable" and the implementation's response was a reduction-step cap (see Q3) — [Augustsson 1998, p.1](https://www.cs.tufts.edu/~nr/cs257/archive/lennart-augustsson/cayenne.pdf#page=1)
- The standard escape hatch, stated as a postulate: MetaRocq's verified checker "relies on a postulate of strong normalization of the reduction relation of PCUIC on well-typed terms." — [MetaRocq README](https://github.com/MetaRocq/metarocq)
- Decidability recovered by restricting the *mode theory* rather than the terms (MTT, journal version Mar 2026): "MTT admits an unconditional normalization algorithm and conversion of normal forms is decidable if conversion is decidable in the mode theory. As corollaries, we show that type constructors in MTT are always injective and that type checking is decidable when the mode theory is decidable." — [Gratzer, "Normalization for multimodal type theory", arXiv:2301.11842, p.1](https://arxiv.org/pdf/2301.11842#page=1); the LMCS header in the fetched PDF reads "Volume 22, Issue 1, 2026 ... Published Mar. 17, 2026".

### Inferences
- For a disp type given as an arbitrary tree-calculus recognizer, the set {v : type accepts v} is in general Σ⁰₁ (accept is semi-decidable by running), and {v : type refutes v} is likewise Σ⁰₁; "proven for all v" (Π⁰₂ in the worst case) is not reachable by the stream alone. So the checker's honest outputs are exactly disp's three: a found refutation (checkable), a bounded non-refutation (k-approximant membership, Q3), and "proven" only when an external totality/termination argument exists (e.g. a type whose recognizer is structurally recursive, or a MetaRocq-style normalization postulate for a fragment).
- Statman's PSPACE bound matters for the *optimizer*: even in the simply typed fragment, searching for an inhabitant of a type is PSPACE-complete, so "program search under the type as constraint" is hard already before undecidability enters.
- Gratzer's result shows a modern pattern for keeping decidability in a *parameterized* theory: push the undecidable part into the parameter (mode theory) and prove "decidable if the parameter is decidable". A disp analogue: "the checker terminates if the type's recognizer terminates".

### Gaps
- Statman 1979 (Elsevier), Urzyczyn 1997 (Springer) and Löb 1976 (JSL) could not be fetched; Semantic Scholar confirmed Statman's and Urzyczyn's titles/venues (see unverified list). The DIKU lecture notes are used as the verified primary text for all three theorems.
- Meyer & Reinhold's "Type is not a type" (1986) and other sources on undecidability of Type:Type systems were not fetched.

## Q7. Types over a combinatory substrate: realizability and partial combinatory algebras, Jay's tree calculus and intensional computation. What does it mean for a type to be a recognizer over all terms of a reflective calculus?

### Takeaway
Realizability gives the standard semantics in which a type is a set of untyped realizers from a partial combinatory algebra (PCA), with "modest sets/assemblies" as the categorical packaging; QTT (Q2) already uses a linear variant of this to model grades. Jay's tree calculus is a PCA-like substrate with one extra property: equality of closed normal forms (and size, and self-interpretation) is *definable inside the calculus*, which Jay argues the λ-calculus lacks. His book explicitly frames program analyses, including type systems, as reflective programs, and sketches a Tait-style simple type system for tree calculus by tagging terms with types. A type-as-recognizer in disp is therefore an *intensional* realizability predicate: a program that may inspect the structure of a candidate term, not just apply it.

### Cited Findings
- PCAs as the general model class (Bauer's lecture notes): "The Type I and Type II models of computability are the ones that are used almost exclusively in computable mathematics. General realizability theory, however, considers a wider class of models, called (typed) partial combinatory algebras (pca). There are many examples of pca's from topology, domain theory and the theory of programming languages." Kleene's first and second PCAs are named K1 and K2. — [Bauer, "Realizability as the Connection between Computable and Constructive Mathematics", p.5](https://math.andrej.com/data/c2c.pdf#page=5)
- Assemblies and modest sets (same notes): "In realizability theory representations are also known as modest sets, and the multi-valued ones as assemblies." — [Bauer, p.6](https://math.andrej.com/data/c2c.pdf#page=6)
- QTT is given "a realizability semantics using a variant of Linear Combinatory Algebras, refining the usual realizability semantics of Type Theory by accurately tracking resource behaviour." — [Atkey 2018, p.1](https://bentnib.org/quantitative-type-theory.pdf#page=1)
- Tree calculus in one sentence (book, draft on GitHub, fetched 2026-10-09): "The resulting theory of computation is both simple and powerful: simple because it is based on three equations only; powerful because one program can query the internal structure of another, using a mix of extensional and intensional techniques." — [Jay, "Reflective Programs in Tree Calculus", p.5](https://raw.githubusercontent.com/barry-jay-personal/tree-calculus/master/tree_book.pdf#page=5)
- Program analyses, including type systems, as reflective programs (same book, Ch.1): "Full support for reflective programs, where source programs and executables can be identified, will allow developers with standard tools to add program analyses, including type systems and evaluation strategies, without having to redefine or re-implement the programming language." and "In tree calculus, a program analysis is a reflective program." — [Jay, book pp.8–9](https://raw.githubusercontent.com/barry-jay-personal/tree-calculus/master/tree_book.pdf#page=8)
- The book's typed fragment is explicitly preliminary (§5.5 "Simple Types"): "This section will introduce a simple type system, in the style of William Tait, that supports booleans, natural numbers and functions, and use it to type a few terms of tree calculus by tagging terms with their types. Much remains to be done, even for simple types." — [Jay, book §5.5](https://raw.githubusercontent.com/barry-jay-personal/tree-calculus/master/tree_book.pdf)
- Machine-checked proofs accompany the book: the repository README is titled "Tree_Calculus_Proofs" — [barry-jay-personal/tree-calculus](https://github.com/barry-jay-personal/tree-calculus#tree_calculus_proofs)
- The intensional thesis (Jay & Vergara, arXiv 2014, revised PDF dated 2018): "any model of computability in which equality is not definable, such as the λ-models underpinning higher-order programming languages, is not equivalent to the Turing model. However, a modern combinatory calculus, the SF-calculus, can define equality of its closed normal forms, and so yields a model of computability that is equivalent to the Turing model." and "By supporting a form of intensional computation, it suggests a more powerful approach to programming language design." — [Jay & Vergara, "Confusion in the Church-Turing Thesis", arXiv:1410.7103](https://arxiv.org/pdf/1410.7103#page=12) (the minted fragment for "SF-calculus" is p.12; the quoted sentences are from the abstract and §1).
- The book's Part II relates tree calculus to SF-calculus: chapter "10 Divide-and-Conquer in SF-Calculus" with sections "Translation from Tree Calculus" and "Translation to Tree Calculus" (table of contents). — [Jay, book](https://raw.githubusercontent.com/barry-jay-personal/tree-calculus/master/tree_book.pdf)

### Inferences
- In realizability a type is already "a set of untyped terms"; what disp adds is that the *membership test itself* is a term of the same calculus. In Kleene's K1 this is impossible in general (membership is not decidable), so realizability types are semantic, not recognizers. Tree calculus's definable equality and self-interpretation are what make a *syntactic* recognizer expressible for decidable properties, and a *semi-decidable* one (run and see) for the rest. This is why disp's "type = program" is coherent on this substrate and would not be on a pure λ-calculus substrate per Jay & Vergara.
- A recognizer over *all* terms (not only normal forms) inherits the Q6 limits: it can inspect structure (intensional, terminating) and it can apply (extensional, possibly non-terminating). The budget only matters for the second kind of step; a design consequence is that a checker should prefer intensional tests first, which are total.
- Jay's own typed tree calculus is, as of the fetched draft, a Tait-style simple type system by tagging and he flags it as unfinished; there is no published dependent type theory over tree calculus to compare against. disp's type-as-recognizer is a different (realizability-style) approach rather than an extension of Jay's.

### Gaps
- Kleene's 1945 realizability paper and van Oosten's monograph were not fetched (publisher-blocked); Bauer's notes are the verified source for PCAs/assemblies.
- The book draft on GitHub carries no version date in the extracted text; I could not establish whether §5.5 has changed since the Coq Discourse announcement.

## Q8. Modular and data-defined type theories: LF, Dedukti/λΠ-modulo, Andromeda and general type theories, type theory in type theory, 2LTT, MTT, Cocon, MetaCoq/MetaRocq, Lean 4. What is gained by making the type theory a parameter, and what breaks?

### Takeaway
Two families. *Logical frameworks* (LF 1987/1993; Dedukti/λΠ-modulo; Andromeda 2) make the object theory a *signature* (constants, plus rewrite rules in Dedukti, plus arbitrary user rules in Andromeda) checked by a fixed small kernel; what you gain is logic-independent tooling and cross-system proof exchange, what you lose is that consistency and canonicity of the *object* theory are not guaranteed by the framework (Andromeda is explicit that it checks user-definable theories and that normalization lives outside the trusted nucleus). *Parameterized type theories* (MTT by a mode theory; 2LTT inner/outer; general type theories by Bauer–Haselwarter–Lumsdaine) prove metatheory once for the whole family, conditional on the parameter (MTT: canonicity for every mode theory; decidable type checking iff the mode theory is decidable). *Type theory inside the host* (Altenkirch–Kaposi QITs; Cocon; MetaRocq; Lean 4 metaprogramming and Lean4Lean) lets the checker be a verified or at least inspectable program, at the price of either a strong-normalization postulate (MetaRocq) or a trusted compiler/kernel boundary (Lean).

### Cited Findings
- LF (LFCS report 1991; LICS 1987; JACM 1993): "Logics are represented in LF via a new principle, the judgements as types principle, whereby each judgement is identified with the type of its proofs. ... rules are viewed as proofs of higher-order judgements and proof checking is reduced to type checking. The practical benefit of our treatment of formal systems is that logic-independent tools such as proof editors and proof checkers can be constructed." — [Harper, Honsell, Plotkin, "A Framework for Defining Logics", ECS-LFCS-91-162](https://www.lfcs.inf.ed.ac.uk/reports/91/ECS-LFCS-91-162/#spacer)
- λΠ-calculus modulo theory (Dedukti overview, arXiv Nov 2023): "In the λΠ-calculus modulo theory, the contexts contain variable declarations—like in the λΠ-calculus—and also rewrite rules. The conversion rule is extended in order to take these rewrite rules into account." Purpose: expressing many systems' proofs in one framework "is also a way to audit formal proofs develop in these systems by checking them in a different, independent, system. We show this way that the logical framework approach scales up and that it is mature enough to start imagining a single distributed library of formal proofs expressed in different theories, developed in different systems, but formulated in a single framework." — [Assaf et al., "Dedukti: a Logical Framework based on the λΠ-Calculus Modulo Theory", arXiv:2311.07185, p.3](https://arxiv.org/pdf/2311.07185#page=3)
- Dedukti/Lambdapi team scope (site fetched 2026-10-09): "We develop the Dedukti proof checker and the Lambdapi proof assistant. We study proof systems interoperability and develop various translators between existing proof assistants (Agda, HOL-Light, Isabelle, Lean, Rocq, etc.) using Dedukti and Lambdapi." — [Deducteam](https://deducteam.gitlabpages.inria.fr/)
- Andromeda 2 (site fetched 2026-10-09): "Andromeda 2 is a proof checker for user-definable dependently-typed theories. It follows the design of LCF-style theorem provers. There is an abstract datatype judgement whose values can only be constructed by a nucleus, a small trusted component of the proof checker. The user interacts with the nucleus by writing programs in a high-level, statically typed Andromeda meta-language (AML). Normalization, unification, and other proof development techniques reside o[utside the nucleus]" — [andromeda-prover.org](https://www.andromeda-prover.org/)
- General definition of dependent type theories (arXiv Sep 2020): "we give three main definitions: raw type theories, a minimal setup for discussing dependently typed derivability; acceptable type theories, including extra conditions ensuring well-behavedness; and well-presented type theories, generalising how in traditional presentations, the well-behavedness of a type theory is established step by step as the type theory is built up. Following these, we show that various fundamental fitness-for-purpose metatheorems hold in this generality. Much of the present work has been formalised in the proof assistant Coq." — [Bauer, Haselwarter, Lumsdaine, arXiv:2009.05539, p.1](https://arxiv.org/pdf/2009.05539#page=1)
- MTT (LICS 2020; LMCS 2021): "MTT can be instantiated by a mode theory, a strict 2-category describing modes, modalities, and natural transformations between these modalities." Metatheory: "We prove the consistency of MTT and establish canonicity through an extension of recent type-theoretic gluing techniques. These results hold irrespective of the choice of mode theory, and thus apply to a wide variety of modal situations." — [Gratzer, Kavvos, Nuyts, Birkedal, "Multimodal Dependent Type Theory", arXiv:2011.15021, p.1](https://arxiv.org/pdf/2011.15021#page=1)
- MTT normalization and the price of parameterization (LMCS Mar 2026): "While this flexibility allows MTT to accommodate many interesting calculi, it becomes proportionally more challenging to prove metatheoretic results about MTT." Result: "type checking is decidable when the mode theory is decidable." — [Gratzer, arXiv:2301.11842, p.1](https://arxiv.org/pdf/2301.11842#page=1)
- Two-level type theory (arXiv 2017; MSCS 2023): 2LTT "combines two different type theories. We refer to them as the 'inner' and the 'outer' type theory. In our case of interest, the inner theory is homotopy type theory (HoTT) ... The outer theory is a traditional form of type theory validating uniqueness of identity proofs (UIP)." — [Annenkov, Capriotti, Kraus, Sattler, arXiv:1705.03307, p.1](https://arxiv.org/pdf/1705.03307#page=1)
- Type theory in type theory (POPL 2016): "Our formalisation of type theory avoids refering to preterms or a typability relation but defines directly well typed objects by an inductive definition." using "quotient inductive types (QITs)". — [Altenkirch & Kaposi, author PDF p.1](https://people.cs.nott.ac.uk/psztxa/publ/tt-in-tt.pdf#page=1)
- Cocon (LICS 2019): "We mediate between HOAS representations and computations using contextual modal types. Our type theory also supports an infinite hierarchy of universes and hence supports type-level computation thereby providing metaprogramming and (small-scale) reflection. Our main contribution is the development of a Kripke-style model for Cocon that allows us to prove normalization." — [Pientka, Thibodeau, Abel, Ferreira, Zucchini, arXiv:1905.02617, p.1](https://arxiv.org/pdf/1905.02617#page=1)
- MetaRocq (README fetched 2026-10-09): provides "A formalization of the typing rules reflecting the ones of Rocq" and a "Safe Checker: Implementation of a fuel-free and verified reduction machine, conversion checker and type checker for PCUIC. This relies on a postulate of strong normalization of the reduction relation of PCUIC on well-typed terms. The checker is shown to be correct and complete w.r.t. the specification" — [MetaRocq/metarocq](https://github.com/MetaRocq/metarocq); project site: [metarocq.github.io](https://metarocq.github.io/)
- Lean 4 (CADE 2021): "Users may also extend and modify the elaborator using Lean itself. Lean has a relatively small trusted kernel, and the rich API allows users to export their developments to other systems and implement their own reference checkers." — [de Moura & Ullrich, "The Lean 4 Theorem Prover and Programming Language", p.1](https://lean-lang.org/papers/lean4.pdf#page=1)
- Lean4Lean (arXiv Mar 2024, v3 Sep 2025; TYPES 2025, LIPIcs doi:10.4230/LIPIcs.TYPES.2025.2 per Semantic Scholar): the kernel "was extended with various features for performance reasons like bignum arithmetic, nested inductive types, and primitive projections, and unfortunately some soundness bugs crept in during the process and Lean's record is no longer spotless. Another thing that was lost during the port was the external checkers" — [Carneiro, "Lean4Lean: Verifying a Typechecker for Lean, in Lean", arXiv:2403.14064, p.1](https://arxiv.org/pdf/2403.14064#page=1)
- Hazel (POPL 2019) as a live system that evaluates incomplete programs: the paper's core contribution is "a core calculus, Hazelnut Live, that supports evaluating incomplete expressions"; a result that cannot progress is "indeterminate, because it is not yet a value, nor can it take a step due to holes in elimination positions." — [Omar, Voysey, Chugh, Hammer, "Live Functional Programming with Typed Holes", arXiv:1805.00155, p.1](https://arxiv.org/pdf/1805.00155#page=1)

### Inferences
- What is gained by making the type theory a parameter, per the sources: one kernel for many logics (LF, Dedukti), cross-checking the same proof in an independent system (Dedukti's "audit"), one metatheory proof for a whole family (MTT canonicity for every mode theory), and a checker that is itself a verified program (MetaRocq) or a swappable external one (Lean 4 exports; Lean4Lean).
- What breaks: (i) *consistency/canonicity of the object theory* are no longer the framework's business — Andromeda's nucleus guarantees only that derivations follow the user's rules; Dedukti must trust that the user's rewrite system is confluent and terminating; MTT's canonicity is unconditional but its decidability is conditional on the parameter. (ii) *The trusted core moves*: in Lean it is the C++ kernel plus, for `native_decide`, the compiler (Q4); in MetaRocq it is a strong-normalization postulate; in Andromeda it is the nucleus with normalization pushed to untrusted AML. (iii) Lean4Lean documents that even a "small trusted kernel" accumulated soundness bugs when extended for performance, and that external checkers were lost in the Lean 3→4 port — i.e. performance changes to the canonical checker are the historical source of trust failures.
- For disp: Andromeda's split (tiny nucleus that only constructs judgements; all normalization and search outside it) is the closest existing architecture to "the type checker is a program to be optimized and swapped": fast checkers live outside and must produce nucleus-accepted evidence. MTT's "decidable iff the parameter is decidable" is the shape of theorem disp can hope for: "terminates iff the type's recognizer terminates".
- Hazel's "indeterminate" result is an existing formal status for "evaluation could not proceed", though its cause is holes rather than budget; it shows that a three-valued evaluation outcome (value / stuck-indeterminate / error) can be given a clean operational semantics with metatheory.

### Gaps
- "Coq Coq Correct!" (POPL 2020) is ACM-only and could not be fetched; the MetaRocq README is used instead. The MetaCoq JAR 2020 paper was not fetched.
- Andromeda 2's accompanying paper (Bauer, Haselwarter et al.) was not fetched; the project site and the general-type-theories paper stand in.
- No source was found that compares the *performance* of a type theory-as-data checker (Dedukti/Andromeda) against a hard-coded one; "what breaks" above is about trust and metatheory, not speed.
